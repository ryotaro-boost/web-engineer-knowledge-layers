機能要件を渡されたら、関連するトピックの知識を踏まえた、AIコーディングエージェントへのプロンプト雛形を提示してください。

## 入力
$ARGUMENTS（形式: `機能要件の説明` または `トピック名: 機能要件`）

例:
- `ユーザー登録APIを作りたい`
- `認証と認可: JWT認証のミドルウェアを書く`
- `データアクセス層: ユーザー一覧のページネーション`

## 手順

1. 入力から機能要件を抽出し、関連トピックを特定する（複数の場合は最も中心的なもの1-2個）
2. 関連トピックの以下セクションを読む:
   - `誤解されやすいポイント`
   - `設計のベストプラクティス`
   - `AIエージェントとの協働 → 効くプロンプトの型`
   - `AIエージェントとの協働 → AI実装のアンチパターン`
3. `_anti-patterns/_index.md` の横断的レビュー観点を参照する
4. 以下のフォーマットでプロンプト雛形を生成する

## 出力フォーマット

```
## 関連トピック
- [[XXX]]: なぜこのトピックが関連するか
- [[YYY]]: （あれば）

## 推奨プロンプト雛形

\`\`\`
# 前提（プロジェクトの状況・既存コード規約）
- ＜学習者が埋める部分。例: 言語・FW・既存規約の場所＞
-

# やってほしいこと
- ＜要件を整理した形で記述＞
-

# 守ってほしい制約
- ＜トピック固有の落とし穴を回避するための制約＞
- ＜AIアンチパターンを回避するための制約＞
-

# 完了の判断基準
- ＜動作確認の基準＞
- ＜セキュリティ・パフォーマンスの基準＞
- ＜テストの基準＞
-
\`\`\`

## このプロンプトの意図

### なぜこの「制約」を入れたか
- 制約1: ... を防ぐため（[[XXX]] の「誤解されやすいポイント」より）
- 制約2: ... を防ぐため（AIアンチパターン「YYY」より）

### なぜこの「判断基準」を入れたか
- 判断基準1: ... を確認するため
- 判断基準2: ... を確認するため

## 学習者へのコメント
- このプロンプトを実際に使って、AIに書かせてみる
- 生成されたコードを `/review-ai-code` でレビューする
- 不足を埋める追プロンプトを設計する
```

## 注意事項

- 学習者が「自分でプロンプトを書ける」ようになるのが目的なので、雛形を渡すだけでなく **意図の解説** を必ず添える
- 「守ってほしい制約」は、関連トピックの「誤解されやすいポイント」「アンチパターン」から具体的に引く（一般論で済ませない）
- 「完了の判断基準」は、AIが「動いた」と報告しても本当に正しいかを **学習者自身が判断できる粒度** にする
- プロンプトをコピペで使えるよう、コードブロック形式で提示する
- 関連トピックが見つからない / 教材外の領域の場合は、その旨を明示し、汎用的な雛形を提示する
- 雛形には「学習者が埋める部分」と「教材から導出した固定部分」を区別して示す
