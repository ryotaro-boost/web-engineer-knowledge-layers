指定されたトピックドキュメントの密度突出した節を抽出し、`details/`への切り出しを提案してください。

## 入力
$ARGUMENTS（形式: `トピック名` または `Layer配下のパス`、例: `API設計-REST-GraphQL`, `Layer4/Backend/認証と認可`）

## 手順

1. 対象ファイルを読み、章ごとの行数・コードブロック数・比較表の規模を計測する
2. 以下を切り出し候補として抽出する:
   - **4-5言語並列のコード例**（主要1言語以外を切り出し）
   - **30行を超える比較表**
   - **歴史的経緯・規格進化の節**
   - **派生概念や周辺概念の解説**（本筋からの脱線が大きいもの）
   - **AIに任せられる定型実装の細部**（人間が読み込む必要が低いもの）
3. 各候補について、以下を提案する:
   - 切り出し先 `details/XXX.md` のファイル名（命名規約: 日本語、英語略語はハイフン区切り、スペースなし）
   - 親トピック側に残す要約・ナビゲーション文（2-4行）
   - 親トピック本文中での `[[XXX]]` インラインリンクの埋め込み位置
4. 切り出し後の本文行数の見込みを示す（目安: 200-350行）
5. ユーザーに提案を提示し、承認後に実施する

## 切り出しの判断軸

| 残す | 切り出す |
|------|---------|
| 設計選定・トレードオフ | 言語別実装の細部 |
| 落とし穴・誤解されやすいポイント | 歴史的経緯 |
| セキュリティ判断 | 周辺概念の深掘り |
| 「AIに任せやすいか」の判断材料 | AIに任せられる定型 |
| 人間判断が要る部分 | 主要1言語以外のコード例 |

**本文に残すべきは「AI協働時代に人間が読むべき内容」。** 例えば「正しいSQLの書き方」はdetails化候補だが、「インジェクション攻撃の仕組み」は本文に残す。

## 注意事項

- 元の本文の意味を変えてはならない（情報の損失なく、配置を変えるだけ）
- 切り出し先が既に存在するか必ず確認する（Glob で `details/XXX.md` を検索、重複作成を避ける）
- 親トピックの `[[XXX]]` リンクは末尾一覧ではなく **本文中インライン** に配置する
- 図解は Mermaid 記法のまま保持する（アスキーアート化禁止）
- フロントマター: 切り出した details には `parent: "[[親トピック名]]"`, `type: detail`, `created: 今日の日付` を必ず含める
- 既存detailsに統合すべき内容なら、新規作成ではなく既存ファイルへの追記を提案する
- 自動では適用せず、ユーザー承認後に実施すること

## 報告フォーマット

```
## 現状の密度分析
- 全体行数: XXX行
- 章別の行数: ...
- 突出している章: ...

## 切り出し候補
### 候補1: 「XXX」セクション (X行)
- 切り出し先: `details/YYY.md`
- 切り出し理由: ...
- 親トピックに残す要約案: ...
- インラインリンク埋め込み位置: ...

### 候補2: ...

## 切り出し後の見込み
- 本文行数: XXX行 → YYY行
- 新規details: N個
```
