# データ構造とアルゴリズム

> **一言で言うと:** データをどう整理し（データ構造）、どう処理するか（アルゴリズム）の基礎で、「検索が O(1) なのか O(n) なのか」がシステム全体のスケーラビリティを決める。

## 3分で全体像

- **何を解決する技術か:** プログラムの「データの持ち方」と「処理手順」を、性能と保守性の両方で破綻させない選択を可能にする
- **代表的な使用シーン:** 大量データの検索・集計・結合、リスト仮想化、キュー処理、木構造の走査（カテゴリツリー、ファイルシステム、JSONパース）
- **これだけは覚える3つ:**
    1. 「**何を最も頻繁にやるか**」でデータ構造を選ぶ（検索が多いならハッシュ、順序付きアクセスが多いなら配列、階層なら木）
    2. **ネストしたループは O(n²) を疑う**。一方を Map にすると O(n+m) に落ちる
    3. **n の現実的な上限を最初に確認する**。n ≤ 数十なら線形探索で十分
- **AIに任せやすいか:** **任せやすい** — 既知パターン（CRUD、ハッシュ化、ループ最適化）はAIが書ける。N+1 や計算量爆発の検出もAIコードレビュー観点経由で AI にレビューさせれば検知可能。人間の最終判断は「実データの分布を踏まえたデータ構造の最終選定」と「AIレビュー結果の採否」
- **詰まったらここを読む:** [[計算量-BigO]] / [[ハッシュテーブル]] / [[DFSとBFS]]

## なぜ必要か

プログラムは突き詰めると「データを受け取り、変換し、返す」ことの繰り返しである。データの持ち方と処理手順を意識しないと、次のような問題が発生する。

- **パフォーマンス崩壊** — ユーザー数が100人のときは動くが、10万人になった途端にレスポンスが数十秒になる。原因の多くは「配列を毎回線形探索している」「ネストしたループで O(n²) になっている」といった構造的な問題。
- **メモリの無駄遣い** — 不要なコピーや不適切なデータ構造の選択で、メモリ消費が爆発する。
- **コードの複雑化** — 適切なデータ構造を使えば数行で済む処理を、配列と if 文の塊で書いてしまい、バグの温床になる。

## どの問題を解決するか

### 問題1: 「探す」コストが高すぎる

最も頻出する操作は「検索」である。配列の[[線形探索]]は O(n) だが、[[ハッシュテーブル]]なら平均 O(1) で済む。

| 操作 | 配列（Array） | ハッシュテーブル（Hash Table） | 二分探索木（BST） |
|------|-------------|--------------------------|----------------|
| 検索 | O(n) | O(1) 平均 | O(log n) |
| 挿入 | O(1) 末尾 / O(n) 先頭 | O(1) 平均 | O(log n) |
| 削除 | O(n) | O(1) 平均 | O(log n) |

### 問題2: 「順序」や「関係性」を表現できない

- **木構造（Tree）** — DOM、ファイルシステム、JSON のパースツリーなど、階層的なデータを表現する。
- **グラフ（Graph）** — SNSの友人関係、ページ間のリンク、マイクロサービス間の依存関係など、多対多の関係を表現する。
- **キュー（Queue）** — ジョブキュー、イベントループのタスクキュー（[[Resources/Study/Layer0-CS基礎/並行性の基本概念|並行性の基本概念]]）、メッセージブローカーなど、「先入れ先出し」の処理順序を保証する。
- **スタック（Stack）** — コールスタック、ブラウザの戻る/進む履歴、undo 機能など、「後入れ先出し」を実現する。

### 問題3: 最適な処理手順がわからない

アルゴリズムは「問題をどの手順で解くか」の定石集である。

- **ソート** — 表示順の並び替え、[[バイナリサーチ]]の前処理、重複排除の前処理。
- **探索** — [[DFSとBFS|深さ優先探索（DFS）と幅優先探索（BFS）]]で木やグラフを走査する。
- **[[動的計画法]]（DP）** — 重複する部分問題を効率的に解く（例：最短経路、編集距離）。

## 他の仕組みとどう関係するか

- **下位レイヤーとの関係:** データ構造はメモリ上のデータ配置そのものである。配列が連続メモリ領域でキャッシュに乗りやすい、リンクリストがポインタで散らばるといった特性は、ハードウェアレベルの知識と直結する。
- **同レイヤーとの関係:** [[計算量-BigO]] はデータ構造・アルゴリズムの「性能を評価する言語」であり、セットで理解する必要がある。[[並行性の基本概念]] では、[[スレッドセーフなデータ構造|スレッドセーフなキューやロックフリーデータ構造]]が重要になる。[[文字コード-UTF8]] の文字列もバイト配列として内部的にはデータ構造の一種。
- **上位レイヤーとの関係:** Layer 1 の [[プロセスとスレッド]] ではキューやスタックが実行管理に使われる。Layer 3 の [[Resources/Study/Layer3-データ永続化/インデックス|インデックス]] は[[B-TreeとB+Tree|B-Tree]]というデータ構造そのもの。Layer 5 の [[パフォーマンス最適化]] ではデータ構造の選択が直接的な改善手段になる。

## 誤解されやすいポイント

1. **「[[ハッシュテーブル]]は常に最速」という思い込み** — ハッシュテーブルの検索は平均 O(1) だが、ハッシュ衝突が多いと O(n) に退化する。また、順序を保持しない（JavaScript の `Map` は挿入順を保持するが、これは言語仕様であってハッシュテーブルの性質ではない）。範囲検索やソート済みデータの走査には二分探索木の方が適している。

2. **「配列は遅い」という過度な一般化** — 配列は連続メモリに格納されるため CPU キャッシュとの相性が良く、小さなデータセットでは理論的に遅いはずの O(n) 操作が、キャッシュミスの多い O(log n) の木構造より速いことがある。実測が大事。

3. **「Web開発ではアルゴリズムは不要」という誤解** — フレームワークが多くを隠蔽しているが、以下のような場面で知識が問われる：
   - APIレスポンスのページネーション設計（オフセット vs カーソル）
   - フロントエンドのリスト仮想化（どのアイテムを描画するかの二分探索）
   - バックエンドのバッチ処理での効率的なデータ結合
   - データベースクエリの最適化（N+1問題の理解）

4. **「ソートは `Array.sort()` を呼べば十分」** — 呼ぶだけなら確かに十分だが、比較関数の書き方を間違える（数値を文字列としてソートしてしまう）、安定ソートかどうかを気にしない、大量データでのソートがボトルネックになっている場合に改善策を知らない、といった問題が起きる。

## 設計のベストプラクティス

### 推奨パターン

- **「何を最も頻繁にやるか」でデータ構造を選ぶ** — 検索が多いならハッシュテーブル、順序付きアクセスが多いなら配列やソート済みリスト、階層構造なら木。[[インターフェース]]（抽象データ型）で操作の契約を定義し、実装を差し替え可能にしておくと、後から最適なデータ構造に切り替えやすい。
- **Set を活用する** — 「この要素は存在するか？」の判定には配列の `includes()` ではなく `Set` を使う。O(n) → O(1)。
- **Map を活用する** — キーが文字列以外（オブジェクト参照など）の場合や、頻繁な追加・削除がある場合は `Object` より `Map` が適切。
- **イミュータブルな操作を意識する** — 特にフロントエンドでは、配列やオブジェクトを直接変更せず新しいものを作る（React の状態管理）。ただしパフォーマンスが問題になる場合はミュータブルな操作も選択肢。
- **[[ジェネリクス]]で型安全なコレクション操作を書く** — `Map<string, User>` や `Set<number>` のように型パラメータを活用し、実行時エラーではなくコンパイル時に型の不整合を検出する。

### アンチパターン

- **配列をマップ代わりに使う** — `users.find(u => u.id === targetId)` を繰り返し呼ぶなら、最初に `Map` に変換しておく。
- **ネストしたループで結合する** — 2つの配列を照合するときに二重ループ O(n²) を書くのではなく、一方をハッシュマップにして O(n) にする。
- **巨大な配列のスプレッド乱用** — `[...bigArray, newItem]` は毎回 O(n) のコピーが発生する。頻繁に行うならパフォーマンスを意識した設計にする。

## AIエージェントとの協働

> このトピックでAIコーディングエージェントと協働するための観点。「AIに何をどこまで任せ、人間は何を判断するか」を整理する。

### AIに任せられる部分 / 人間が判断すべき部分

「実装もレビューもAIに任せられる」前提で人間の最終判断を整理する。

| タスク種類 | 任せ方（実装/レビュー） | 人間の関与 |
|---|---|---|
| 既知パターンの実装（CRUD、Map変換、Setによる重複排除） | 仕様を渡して実装を任せる | 動作確認とエッジケースのテスト |
| ループの計算量改善（O(n²) → O(n)） | 「ハッシュマップ化で改善して」と指示 | 改善が本当に必要か（n の現実的な上限）の判断 |
| **N+1 や計算量爆発の検出** | AIコードレビュー観点でAIにレビューさせる | 指摘の妥当性確認、改善優先度の判断 |
| ソート/探索の標準実装 | 実装を任せる（言語標準を使う） | 安定ソートが必要か等の要件決め。比較関数の正しさはAIレビューに任せ最終確認 |
| データ構造の選定 | 候補とトレードオフをAIに出させる | プロジェクト規約・実データの分布・操作頻度を踏まえて採否を決める |
| データ構造のラッパークラス設計 | 必要性をAIに問う、過剰なら指摘させる | そもそも必要か（標準コレクションで足りるか）を最終判断 |

### AI生成コードのレビュー観点（このトピック固有）

AI生成物を受け取ったとき、最低限ここを見る。

1. **計算量が爆発していないか:** ネストしたループ、ループ内での `find/includes/indexOf`、ループ内のスプレッド `[...arr, item]` を見たら O(n²) を疑う
2. **コレクションをラップしすぎていないか:** 標準 `Map`/`Set`/`Array` で済む処理にクラス・ヘルパー関数が乱立していないか
3. **n の上限を考慮しているか:** 数十件しか来ないデータに対して、Mapやバイナリサーチを導入していないか（早すぎる最適化）

### 効くプロンプトの型

```
# 前提
- TypeScript / Node.js / 既存ユーティリティは src/utils 配下
- このAPIのレスポンスは最大 N 件（実データの分布: 中央値 X, 99パーセンタイル Y）

# やってほしいこと
- 〜のデータ構造で〜の処理を実装

# 守ってほしい制約
- 標準の Map/Set/Array で書ける処理にクラス・ラッパーを作らない
- 1箇所しか使わないユーティリティ関数を切り出さない
- n ≤ 数十なら線形探索で十分（早すぎる最適化禁止）
- 内部関数（外部入力を受けない関数）にバリデーション・null チェックを書かない

# 完了の判断基準
- 既存ユーティリティの再発明をしていない（grep で確認）
- ネストしたループ内での find/includes がない
- 単体テスト（最小ケース・最大ケース・空ケース）が通る
```

### AI実装のアンチパターン

| アンチパターン | なぜ問題か | レビュー観点 / 対策 |
|---|---|---|
| **コレクションの不要なラッパークラス** — 配列や Map をわざわざ `UserCollection` のようなクラスで包み、`add`, `remove`, `findById` 等のメソッドを定義する | 標準コレクションの API で十分な場面で抽象化レイヤーが増え、可読性とメンテナンス性が下がる。使い捨てのスクリプトや小規模モジュールには不要 | 組み込みの `Map`, `Set`, `Array` メソッドをそのまま使う。ドメイン固有のロジック（バリデーション等）がない限りラッパーは作らない |
| **防御的すぎる null チェックの連鎖** — `if (!arr) return []; if (arr.length === 0) return []; ...` のように、起こりえない状態に対するガード節を大量に追加する | コードが肥大化し、本来の処理ロジックが埋もれる。内部関数で入力が保証されている場面では無意味 | システム境界（API入力、ユーザー入力）でのみバリデーションし、内部ロジックでは型システムを信頼する |
| **不要なユーティリティ関数の量産** — `isEmpty(arr)`, `safeGet(map, key, default)` のような薄いラッパー関数を大量に作る | 言語の標準機能（`arr.length === 0`, `map.get(key) ?? default`）で1行で書ける処理を関数化する意味がない | 標準の演算子やメソッドを直接使う。チーム内で統一が必要な場合のみユーティリティを検討 |
| **小さなデータセットへの過剰なアルゴリズム適用** — 10件の配列に対してバイナリサーチを導入したり、Map に変換してから検索する | 小さなデータセットでは線形探索の方がシンプルで十分速い。コードの複雑さが無駄に増える | まず n の現実的な上限を確認する。n ≤ 数十件なら `find()` や `includes()` で十分 |

## 具体例

### 例1: 検索コストの改善 — 配列の[[線形探索]] vs [[ハッシュテーブル|ハッシュマップ]]

**対応する問題:** 問題1「探すコストが高すぎる」

**使用シーン:** EC サイトで注文一覧を表示する際、注文データ（user_id のみ持つ）からユーザー名を引く処理。注文が1万件・ユーザーが5千人いると、配列探索では最大5000万回の比較が走る。

```javascript
// ❌ 配列から毎回検索 — O(n) × ループ回数 = O(n²)
const users = [
  { id: 1, name: "Alice" },
  { id: 2, name: "Bob" },
  { id: 3, name: "Charlie" },
];

const orderUserIds = [3, 1, 2, 1, 3];
const names = orderUserIds.map(id => {
  const user = users.find(u => u.id === id); // 毎回 O(n)
  return user?.name;
});

// ✅ 先にMapに変換 — O(n) + O(m) = O(n+m)
const userMap = new Map(users.map(u => [u.id, u]));
const namesFast = orderUserIds.map(id => userMap.get(id)?.name);
```

### 例2: 重複排除 — Set の活用

**対応する問題:** 問題1「探すコストが高すぎる」

**使用シーン:** フォームのタグ入力で、ユーザーが重複タグを入力していないかバリデーションする。メールの宛先リストで同じアドレスが複数入っていないか確認する。

```javascript
// ❌ 配列の includes — O(n) × n回 = O(n²)
function hasDuplicates(arr) {
  for (let i = 0; i < arr.length; i++) {
    if (arr.slice(i + 1).includes(arr[i])) return true;
  }
  return false;
}

// ✅ Set を使う — O(n)
function hasDuplicates(arr) {
  return new Set(arr).size !== arr.length;
}
```

### 例3: キュー — 非同期タスクの順序制御

**対応する問題:** 問題2「順序や関係性を表現できない」— キューの「先入れ先出し（FIFO）」

**使用シーン:** 画像アップロード機能で、ユーザーが複数ファイルを選択したとき、アップロード順序を保証しつつ同時実行数を制限する。メッセージングアプリでの送信キュー、API のレートリミット付きリクエスト処理なども同じパターン。

```typescript
// アップロードキュー: 最大2件ずつ並行処理し、FIFO順序を保証
class UploadQueue {
  private queue: File[] = [];
  private running = 0;
  private maxConcurrent = 2;

  enqueue(file: File) {
    this.queue.push(file);   // 末尾に追加（enqueue）
    this.processNext();
  }

  private async processNext() {
    if (this.running >= this.maxConcurrent || this.queue.length === 0) return;

    const file = this.queue.shift()!; // 先頭から取り出し（dequeue）
    this.running++;
    try {
      await this.upload(file);
    } finally {
      this.running--;
      this.processNext();
    }
  }

  private async upload(file: File): Promise<void> {
    // 実際のアップロード処理
  }
}
```

### 例4: スタック — undo/redo の実装

**対応する問題:** 問題2「順序や関係性を表現できない」— スタックの「後入れ先出し（LIFO）」

**使用シーン:** テキストエディタやお絵描きアプリの「元に戻す/やり直す」機能。ブラウザの戻る/進むボタンも同じ原理。

```typescript
// undo/redo をスタック2本で実現
class UndoRedoManager<T> {
  private undoStack: T[] = [];
  private redoStack: T[] = [];

  execute(state: T) {
    this.undoStack.push(state); // 現在の状態をスタックに積む
    this.redoStack = [];        // 新しい操作が入ったら redo 履歴は破棄
  }

  undo(): T | undefined {
    const state = this.undoStack.pop(); // 最後に積んだ状態を取り出す（LIFO）
    if (state) this.redoStack.push(state);
    return this.undoStack.at(-1);       // 一つ前の状態を返す
  }

  redo(): T | undefined {
    const state = this.redoStack.pop();
    if (state) this.undoStack.push(state);
    return state;
  }
}
```

### 例5: 木構造の走査 — [[DFSとBFS|BFS と DFS]]の使い分け

**対応する問題:** 問題3「最適な処理手順がわからない」— 探索アルゴリズム

**使用シーン:**
- **BFS（幅優先）** — カテゴリツリーの階層ごとの表示、SNSの「友達の友達」探索、最短経路の探索
- **DFS（深さ優先）** — ファイルシステムの全走査、JSON の深いネストの探索、依存関係の解決

```javascript
// BFS: カテゴリツリーを階層ごとに取得（管理画面のパンくずリスト生成等）
function getByLevel(root) {
  const result = [];
  const queue = [root];

  while (queue.length > 0) {
    const levelSize = queue.length;
    const level = [];
    for (let i = 0; i < levelSize; i++) {
      const node = queue.shift();
      level.push(node.name);
      for (const child of node.children ?? []) {
        queue.push(child);
      }
    }
    result.push(level);
  }
  return result;
}

// DFS: ネストしたカテゴリから特定カテゴリへのパスを探す
function findPath(node, target, path = []) {
  path.push(node.name);
  if (node.name === target) return [...path];

  for (const child of node.children ?? []) {
    const found = findPath(child, target, path);
    if (found) return found;
  }
  path.pop(); // バックトラック
  return null;
}

// 使用例
const categories = {
  name: "全商品",
  children: [
    { name: "家電", children: [
      { name: "PC", children: [{ name: "ノートPC" }] },
      { name: "スマホ" },
    ]},
    { name: "書籍" },
  ],
};

console.log(getByLevel(categories));
// [["全商品"], ["家電", "書籍"], ["PC", "スマホ"], ["ノートPC"]]

console.log(findPath(categories, "ノートPC"));
// ["全商品", "家電", "PC", "ノートPC"]
```

### 例6: ハッシュマップによる集約 — Python

**対応する問題:** 問題1「探すコストが高すぎる」+ 問題3「最適な処理手順がわからない」

from collections import defaultdict, deque

word_count = defaultdict(int)

## 理解度セルフチェック

> 答えられなければ本文に戻る。答えはこのファイル内に必ずある。

1. 配列とハッシュテーブルを「検索 / 挿入 / 削除」の3軸で計算量を比較できるか（30秒で説明）
2. 「`users.find(u => u.id === id)` をループ内で呼ぶ」は O(n²) になる。これを O(n+m) に落とすにはどうするか
3. 次のAI生成コードはどこが過剰か。どう修正すべきか:

```typescript
class UserCollection {
  constructor(private users: User[]) {}
  isEmpty(): boolean { return this.users.length === 0; }
  count(): number { return this.users.length; }
  findById(id: number): User | undefined {
    if (!this.users) return undefined;
    if (this.users.length === 0) return undefined;
    return this.users.find(u => u && u.id === id);
  }
}
```

> [!info] 用語ミニ辞典（解答を読む前に）
> - **`Array.prototype.find()`** — JavaScript の配列メソッド。配列を先頭から順に走査し、条件（例: `u => u.id === 3`）に最初に一致した要素を返す。一致するものがなければ `undefined` を返す。「配列に対して `.find()` と書くと内部で線形探索 O(n) が走る」と覚える
> - **`Map`** — JavaScript 標準の辞書型データ構造。キーから値を O(1) で取り出せる。`new Map(配列)` で初期化、`.get(キー)` で取得、`.set(キー, 値)` で追加
> - **TypeScript の型保証** — 関数の引数に `users: User[]` と型を書くと、TypeScript コンパイラが「`users` は必ず `User` の配列」と保証してくれる。`null` や `undefined` が混入することは型レベルで起きない（外部から `any` 経由で入ってくる場合を除く）

> [!note]- 解答の指針
> **問1: 配列とハッシュテーブルの計算量比較**
>
> 配列は「先頭から1つずつ並んでいるだけ」なので、特定の値を探すには最悪「最後の要素まで全部見る」必要がある。だから検索は O(n)（n は配列の長さ）。
> 一方、ハッシュテーブルは「キーから直接、値が格納されている場所が分かる」仕組みなので、平均的には1回でアクセスできる。これが O(1)。ただしキーが偶然同じ場所に集まる（衝突する）と、その中を線形に探すので最悪 O(n) に退化する。
>
> | 操作 | 配列 | ハッシュテーブル |
> |------|------|------------------|
> | 検索 | O(n) | 平均 O(1) / 最悪 O(n) |
> | 末尾への挿入 | O(1) | 平均 O(1) |
> | 削除 | O(n) | 平均 O(1) |
>
> **問2: ループ内検索を O(n²) から O(n+m) に落とす方法**
>
> 起きていること: 「ユーザー一覧」を持っていて、「注文一覧」と結合したい。注文 1 件ごとに `users.find(u => u.id === id)` を呼ぶと、毎回ユーザー配列を線形探索する。注文が m 件・ユーザーが n 件あると、最悪 m × n 回の比較が走る（O(n × m)、ほぼ O(n²)）。
>
> 解決: 先にユーザー一覧を `Map` に変換しておくと、注文 1 件ごとの検索が「辞書引き」= O(1) で済む。
>
> ```javascript
> // ステップ1: ユーザーを id をキーとする Map に変換（1 回だけ O(n)）
> const userMap = new Map(users.map(u => [u.id, u]));
>
> // ステップ2: 注文ごとに O(1) で引く（合計 O(m)）
> orders.forEach(order => {
>   const user = userMap.get(order.userId);
>   // ...
> });
> ```
>
> 全体の計算量は「Map 構築の O(n) + 注文走査の O(m)」= O(n + m)。`O(n × m)` から `O(n + m)` への改善で、データが大きくなるほど効果が顕著になる。
>
> **問3: AI生成コードの過剰な点 3 つ**
>
> 元のコードは `UserCollection` というクラスで配列を包み、いくつかのメソッドを生やしている。問題は次の3点。
>
> **(a) 不要なラッパークラス**
> `findById(id)` の中身は、JavaScript 標準の `Array.prototype.find()` を呼んでいるだけ。標準で 1 行で書けるものを、わざわざクラスのメソッドにする意味がない。
> 同様に `isEmpty()` は `users.length === 0` で済み、`count()` は `users.length` で済む。**「標準で済むものを自前で包まない」** が原則。
>
> **(b) 防御的すぎる null チェック**
> TypeScript で `users: User[]` と型を付けた時点で、コンパイラが「`users` は `User` の配列で、null も undefined も混入しない」ことを保証している。それなのに以下のチェックがあるのは過剰:
>
> - `if (!this.users) return undefined;` — `this.users` は型上 `User[]` なので、`null` や `undefined` にはならない
> - `if (this.users.length === 0) return undefined;` — そもそも空配列に対して `find` を呼ぶと、自動的に `undefined` が返る。明示的にチェックする意味がない
> - `u && u.id` の `u &&` の部分 — `u` の型は `User` なので、`null` や `undefined` にならない
>
> 「外部入力（ユーザーが送ってきたデータ、API 経由のデータ）」にはバリデーションが必要だが、「内部関数（プログラム内部で型が保証された値を受け取る関数）」では不要。**型システムを信じる**。
>
> **(c) 既存メソッドの再発明**
> 結局このクラスは「`Array.prototype.find` をクラスで包んだだけ」のもの。クラスの存在意義（状態を持つ・複数のメソッドが連携する）が無いなら、ただの関数で十分。
>
> **修正後の最小実装:**
>
> ```typescript
> const findById = (users: User[], id: number) => users.find(u => u.id === id);
> ```
>
> 1 行で意図がそのまま読める。ラッパークラス・null チェック・既存メソッドの再発明、すべて削れた。
