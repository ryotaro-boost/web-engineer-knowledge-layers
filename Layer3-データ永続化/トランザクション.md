# トランザクション

> **一言で言うと:** 複数のDB操作を「全部成功するか、全部なかったことにするか」の単位にまとめる仕組み。送金で「引き落としだけ成功して入金が失敗」を防ぐ。

## 3分で全体像

- **何を解決する技術か:** 並行アクセス・障害・部分失敗のいずれが起きても **データが矛盾した状態にならない** ことを保証する。「途中で電源が落ちても」「同時に他のリクエストが来ても」整合性を維持する
- **代表的な使用シーン:** 送金 / 在庫減算 / 注文作成 / ポイント加算 — **複数テーブル・複数行の更新が「セット」で意味を持つ** あらゆる業務処理。逆に「1行の単純な更新」だけならトランザクションは不要（DB が自動で原子性を保証）
- **これだけは覚える3つ:**
    1. **ACID 4 性質** — 原子性 (Atomicity) / 一貫性 (Consistency) / 分離性 (Isolation) / 永続性 (Durability)。**実務で挙動が変わるのは Isolation のみ**で、設定（分離レベル）次第で読み取り結果が変わる
    2. **境界の引き方が設計判断** — トランザクションは「どこから始まりどこで終わるか」が要。長時間保持はロック競合を生み、短すぎると整合性が崩れる。**外部 API 呼び出しやユーザー入力待ちはトランザクション内に含めない**
    3. **Read-Modify-Write は楽観 / 悲観ロックが必須** — 「残高を読む → 引き算する → 書く」のような3ステップは、ロックなしでは同時アクセスでデータが壊れる。`SELECT ... FOR UPDATE` か version カラムでの楽観的制御を明示する
- **AIに任せやすいか:** **一部任せられる** — `BEGIN`/`COMMIT`/`ROLLBACK` の構文や ORM のトランザクション API は AI が高品質に書ける。ただし **「境界をどこに引くか」「分離レベルをどれにするか」「楽観 vs 悲観のどちらを選ぶか」は実データの並行性パターン・整合性要件・性能制約に依存** するため人間判断が要る。AI 生成コードはAIコードレビュー観点で「楽観/悲観ロックの欠落」「外部 API 呼び出しがトランザクション内に混入」「リトライがべき等でない」を必ず検出する
- **詰まったらここを読む:** [[RDB]] / [[並行性の基本概念]] / [[データアクセス層]]

## なぜ必要か

トランザクションがなかったら何が困るか — 銀行の送金処理を例に考える。「口座Aから1000円引く → 口座Bに1000円足す」を独立した2つの SQL 文として実行するとき、間に以下が起こりうる:

- **電源断 / プロセスクラッシュ** — 引き落としは成功したが、入金前にサーバが落ちる → 1000円が消える
- **同時実行による干渉** — 別のリクエストが同じ口座を読み書きする → 残高がマイナスになる、二重送金される
- **アプリ層の例外** — 引き落とし後にバリデーションエラーが起きても、引き落としだけ残る → 部分失敗

トランザクションは「**この一連の操作はセットとして扱え**」と DB に伝えるための仕組み。COMMIT するまでは中途半端な状態が他者から見えず、どこかで失敗すれば自動的に **全て巻き戻る (ROLLBACK)**。

## どの問題を解決するか

### 1. 原子性 (Atomicity) — 全か無か

`BEGIN` から `COMMIT` までの操作は、**全て実行される** か **1 つも実行されない** かのどちらか。途中で例外が起きれば自動的に巻き戻る。

```sql
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT;
-- どちらかが失敗すれば自動 ROLLBACK
```

### 2. 一貫性 (Consistency) — 制約の維持

トランザクション前後で **NOT NULL / UNIQUE / 外部キー / CHECK 制約** が必ず満たされる。途中で違反した状態が一瞬発生しても、COMMIT 時には必ず満たされる。

### 3. 分離性 (Isolation) — 並行制御

複数のトランザクションが同時に動いても、**互いの中途状態が見えない** ように制御する。何を見せて何を見せないかは **分離レベル** で決まる:

| 分離レベル | Dirty Read | Non-repeatable Read | Phantom Read | デフォルトの DB |
|-----------|-----------|-------------------|-------------|---|
| READ UNCOMMITTED | 起きる | 起きる | 起きる | (使わない) |
| **READ COMMITTED** | 防止 | 起きる | 起きる | **PostgreSQL / Oracle** |
| **REPEATABLE READ** | 防止 | 防止 | (実装依存) | **MySQL InnoDB** |
| SERIALIZABLE | 防止 | 防止 | 防止 | (金融系で利用) |

**実務的には:** 一般的な Web アプリは READ COMMITTED で足り、Read-Modify-Write の競合は明示的なロックで防ぐ。SERIALIZABLE は性能と引き換えに最強の保証を得る選択。

### 4. 永続性 (Durability) — クラッシュ耐性

COMMIT が成功した後はシステム障害（電源断・OS クラッシュ）が起きてもデータは消えない。RDB はこれを **WAL (Write-Ahead Log)** で実現する — 変更は先にログに書かれ、本体への反映は後追い。

詳細な ACID の挙動・SQL 例・ロック戦略は [[details/トランザクション|details/トランザクション.md (深掘り)]] に集約している。

## 誤解されやすいポイント

1. **「トランザクション = ロック」ではない** — トランザクションは「整合性の単位」、ロックはその実装手段の1つ。MVCC (Multi-Version Concurrency Control) を使う PostgreSQL では多くの読み取りでロックを取らずに分離性を実現する
2. **READ COMMITTED で「同じ行を2回読むと値が違う」のは仕様** — Non-repeatable Read は READ COMMITTED で **防止されない**。これに依存したコードは並行アクセス下で壊れる。同一値を保証したいなら REPEATABLE READ にするか、`SELECT ... FOR UPDATE` で取得時にロックする
3. **`SELECT ... FOR UPDATE` を使えば全部 OK ではない** — `WHERE` 句が **インデックスを使えない** とテーブル全体をロックする。ロック対象が広がりすぎてスループットが激減する。インデックス設計と組み合わせて検討する
4. **オートコミットモードでは BEGIN なしの SQL が即 COMMIT される** — クライアントライブラリやフレームワークによってデフォルト挙動が違う。複数操作を原子的にしたい場合は **必ず `BEGIN` を明示** する。ORM が裏で何をしているか把握する
5. **トランザクション内の例外は `catch` でも握りつぶさない** — `catch (e) {}` で例外を消すと、ROLLBACK が呼ばれず **コネクションがロックを保持したまま放置** される。最低でも明示的に `ROLLBACK` を呼ぶか、再 throw する

## 設計のベストプラクティス

- **境界は短く、明示的に** — `BEGIN` から `COMMIT` までの間に外部 API 呼び出し・ユーザー入力待ち・長時間処理を含めない
- **`取得 → 処理 → 短いトランザクションで更新` の3段** — 整合性が必要な部分だけをトランザクションに閉じ込める
- **Read-Modify-Write は明示的にロック** — 在庫減・残高減・カウンタ更新は `SELECT ... FOR UPDATE` か version カラム
- **ロック取得順序を統一** — 複数行をロックする場合、必ず ID 昇順など決まった順で取得（デッドロック予防）
- **デフォルトの分離レベルを把握** — PostgreSQL は READ COMMITTED、MySQL InnoDB は REPEATABLE READ。フレームワーク経由でも変わらないことを確認
- **イベント発行はアウトボックスで** — 「DB 更新 + メッセージキュー発行」を独立にすると失敗時に不整合が残る。同一トランザクションで `outbox` テーブルに書き、別ワーカーがそれを読んで発行する

### AI生成コードのレビュー観点

1. **Read-Modify-Write にロックが入っているか** — 「読む → 計算 → 書く」のパターンで `SELECT ... FOR UPDATE` か version カラムが使われているか。不在なら同時実行で壊れる
2. **トランザクション内に外部 API 呼び出しが混入していないか** — `await fetch(...)` `httpClient.post(...)` が `BEGIN`/`COMMIT` の間にあったら NG。長時間ロック保持の温床
3. **例外時に明示的な ROLLBACK / コネクション解放があるか** — `try-finally` か defer / using で必ずコネクションを返却。`catch (e) {}` の握りつぶしは禁止

### AI実装のアンチパターン

| アンチパターン | なぜ問題か | レビュー観点・対策 |
|---|---|---|
| Read-Modify-Write でロックなし | 同時アクセスで在庫マイナス・残高超過が起きる | `SELECT ... FOR UPDATE` か version カラムを必須化 |
| トランザクション内に `await fetch(...)` | 外部 API のレスポンス時間中ロック保持 → コネクション枯渇 | 「取得 → 処理 → 短い TX で更新」の3段に分解 |
| 例外を `catch (e) {}` で握りつぶし | ROLLBACK されず整合性崩壊、コネクション漏れ | 最低でもログ出力 + 再 throw、または明示的な ROLLBACK |
| `WHERE` 句にインデックスなしで `FOR UPDATE` | テーブル全体ロック → スループット激減 | EXPLAIN で確認、必要なインデックスを追加 |
| 楽観ロックの「0 行更新時のリトライ」忘れ | 競合時に静かに無視される | アフェクテッドロウ数を確認し、0 ならリトライまたは例外 |

| 長時間トランザクションで MVCC 用の領域圧迫 | 古い版を保持し続けディスク・メモリ膨張 | TX を分割、長時間処理は TX 外へ |

## 具体例

シンプルな送金処理を SQL とアプリケーション層で書く例。**コード詳細は [[details/トランザクション|details/トランザクション.md (深掘り)]] に集約** している (PostgreSQL / TypeScript / Go の実装、悲観/楽観ロックの比較、ロック戦略の使い分け)。

```sql
-- 送金: 口座Aから口座Bへ1000円を移動 (悲観的ロックで競合防止)
BEGIN;

-- 残高を行ロック付きで取得
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;

-- アプリ層で残高チェック (省略) → 不足なら ROLLBACK

UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;

COMMIT;
```

## 理解度セルフチェック

> [!info] 用語ミニ辞典
> - **MVCC (Multi-Version Concurrency Control):** 各行の複数バージョンを保持し、トランザクションごとに「自分が見るべきバージョン」を選ぶ並行制御方式。PostgreSQL / Oracle の核
> - **WAL (Write-Ahead Log):** 変更を本体テーブルへ書く前にログへ書き出す仕組み。COMMIT 後の永続性とクラッシュリカバリの基盤
> - **Phantom Read:** 同じ条件で2回検索すると行数が変わる現象。他のトランザクションが INSERT で新しい行を入れたとき発生
> - **Saga パターン:** 分散トランザクションを「補償操作の連鎖」で実現する手法。マイクロサービス間で2PCを使わず結果整合性を取る選択

**Q1.** 一般的な Web アプリで、PostgreSQL のデフォルト分離レベル (READ COMMITTED) を使ったとき、「同じトランザクション内で同じ行を2回 SELECT したら値が違っていた」という現象は起きうるか？ なぜか？

> [!note]- 解答の指針
> **起きうる**。READ COMMITTED は **Dirty Read のみ防止**し、Non-repeatable Read は防止しない。具体的には:
>
> - TX-A が `SELECT balance FROM accounts WHERE id = 1` で 1000 を取得
> - TX-B が同じ行を 500 に更新して COMMIT
> - TX-A が再度同じ SELECT を実行 → 500 が返る
>
> **なぜそうなるか:** READ COMMITTED は「他の TX が **COMMIT 済み** のデータは見える」という挙動。COMMIT した瞬間に変更が他の TX から見えるため、同一 TX 内でも値が変わる。これに依存したロジック（残高を読んで → 計算して → 書く）は同時アクセス下で壊れる。**回避策:** REPEATABLE READ に上げるか、最初の SELECT で `FOR UPDATE` を付ける。

**Q2.** 次のうち、トランザクション内に含めても問題ないものはどれか？ 複数選択可。
- (a) DB の複数テーブルへの UPDATE
- (b) 外部 API への決済リクエスト
- (c) 計算ロジック (アプリ層)
- (d) ユーザーの入力待ち
- (e) Redis への書き込み

> [!note]- 解答の指針
> **答え: (a) と (c)**。
>
> - **(a) ✅** トランザクションの本来の用途。複数テーブルの整合性を保つ
> - **(b) ❌** 外部 API は応答時間が読めず、ロックを長時間保持する → コネクション枯渇 / デッドロック頻発。決済は **トランザクション後** または **アウトボックスパターン**で
> - **(c) ✅** 短時間ならば問題ない。ただし重い計算はトランザクション外に出すのが望ましい
> - **(d) ❌** 数秒〜数分の入力待ちは致命的。ユーザー操作が完結してから別トランザクションで確定する
> - **(e) ❌** Redis は別ストレージ。RDB のトランザクションには参加しない。**書き込みが失敗してもロールバックされない**ため、整合性が崩れる。Redis への書き込みは TX COMMIT 後に行い、それ自体の失敗対策（リトライ・補償）を別途設計する

**Q3 (AI生成コードレビュー).** AI に「在庫の引き当て処理」を頼んだら以下のコードが返ってきた。何が問題か？ 修正方針を示せ。

```typescript
async function reserveStock(productId: number, qty: number) {
  const tx = await db.beginTransaction();
  try {
    const stock = await tx.query("SELECT stock FROM products WHERE id = ?", [productId]);
    if (stock < qty) {
      throw new Error("在庫不足");
    }
    // 配送先API に在庫の確保を通知
    await fetch(`https://shipping.example/reserve`, {
      method: "POST",
      body: JSON.stringify({ productId, qty }),
    });
    await tx.query("UPDATE products SET stock = stock - ? WHERE id = ?", [qty, productId]);
    await tx.commit();
  } catch (e) {
    await tx.rollback();
    throw e;
  }
}
```

> [!note]- 解答の指針
> **3つの問題:**
>
> 1. **`SELECT` が `FOR UPDATE` でない (楽観/悲観ロックなし)** — 同時に2つの注文が来たとき、両方が「在庫 10 個ある」と読んで両方が引き算 → 在庫が 2倍引かれる (オーバーセール)。**修正:** `SELECT stock FROM products WHERE id = ? FOR UPDATE` にして行ロックを取得
> 2. **トランザクション内に外部 API 呼び出し (`await fetch(...)`)** — 配送 API のレスポンスを待つ間、行ロックを保持し続ける。配送 API がタイムアウトするとロックが数秒〜数十秒も持続し、他のリクエストが全て待たされる。**修正:** 外部 API 呼び出しは TX 外に出す。具体的には: TX で `outbox` テーブルにイベントを書き込み、別ワーカーがそれを読んで配送 API を呼ぶ (アウトボックスパターン)
> 3. **配送 API の失敗時の補償が不在** — TX が COMMIT 済みなら DB は確定。だが配送 API が後で失敗したら？ 補償操作 (在庫を戻す) が必要。**修正:** Saga パターンか、配送がべき等な前提で `outbox` のリトライで対処
>
> **なぜそうなるか:** AI は「ハッピーパスの実装」を学習データから出力しがち。**並行性 (同時アクセス)・障害 (外部 API 失敗) の2つは AI が見落としやすい代表的な観点**。レビューでは必ずこの2軸で問う。
