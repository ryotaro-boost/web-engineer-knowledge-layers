# エラーハンドリング

> **一言で言うと:** 「失敗は必ず起きる」という前提のもと、エラーを握りつぶさず、適切な粒度でキャッチし、ユーザーには分かりやすく・ログには詳細に記録する設計手法。エラーを「捕まえる」のではなく「**何を伝え、何を隠し、何をリトライするか**」を設計する。

## 3分で全体像

- **何を解決する技術か:** 本番環境で必ず起きる失敗（DB障害・外部API停止・想定外入力・ハードウェア故障）に対し、(a) ユーザーに行動指針を返す、(b) ログに調査情報を残す、(c) 一時障害ならリトライする、という3つを **コードに分散させずに集約** する
- **代表的な使用シーン:** REST/GraphQL API のエラーレスポンス設計、外部 API 呼び出しのリトライ、決済・在庫など整合性が重要なトランザクションのロールバック、SRE オンコール時の障害切り分け
- **これだけは覚える3つ:**
    1. **エラーは「回復可能 / 不能」で分類** — バリデーションや在庫切れは 400 系で具体的に、null参照やインフラ障害は 500 系で汎用メッセージ + ログ詳細。リトライ可否（4xx は不可、5xx は可）と直結する
    2. **ユーザー向けレスポンスとログは情報量を分離** — レスポンスは「何をすべきか」、ログは「なぜ起きたか（スタックトレース・コンテキスト・リクエストID）」。スタックトレースをレスポンスに含めるのは内部構造の漏洩
    3. **ハンドラ内 try-catch を散らさない** — フレームワーク標準の集約機構（Express の 4 引数ミドルウェア・Laravel `withExceptions`・Rails `rescue_from`・Go の handler ラッパー）でエラー型 → HTTPステータス変換を1箇所に。各ハンドラは **「エラーを投げるだけ」**
- **AIに任せやすいか:** **一部任せられる** — エラー型階層・ミドルウェア・リトライ実装は AI が高品質に書ける。一方「**握りつぶしと詳細露出**」が AI 生成コードで頻出する2大事故であり、`/review-ai-code` で `catch (e) {}` `return []` `err.stack` のレスポンス露出を必ず検出する
- **詰まったらここを読む:** [[ルーティングとミドルウェア]] / [[HTTP-HTTPS]] / [[バリデーション]]

## なぜ必要か

本番環境では、あらゆるものが壊れる。DBが落ちる、外部APIがタイムアウトする、ユーザーが想定外の入力を送る、ディスクが埋まる。エラーハンドリングがなければ、次のことが起きる。

- アプリケーションが**無言でクラッシュ**し、ユーザーにはブラウザのデフォルトエラー画面が表示される
- エラーの**原因が特定できない** — どこで何が失敗したのかの情報が残っていない
- 部分的な処理が**中途半端な状態で放置**される（例：決済は完了したが在庫は減っていない）
- スタックトレースやDB情報が**ユーザーにそのまま表示**され、セキュリティホールになる
- 開発者が障害対応時に**再現も調査もできない**

エラーハンドリングとは「壊れたときにどう振る舞うか」を設計することであり、正常系の設計と同等に重要。

## どの問題を解決するか

### エラーの分類

エラーの性質を正しく分類することが、適切なハンドリングの第一歩。

```mermaid
graph TD
    A["エラー"] --> B{"回復可能か?"}
    B -->|Yes| C["回復可能エラー<br/>(Recoverable)"]
    B -->|No| D["回復不能エラー<br/>(Unrecoverable)"]
    C --> C1["バリデーションエラー"]
    C --> C2["ビジネスロジックエラー<br/>(在庫切れ等)"]
    C --> C3["一時的な外部障害<br/>(リトライで回復)"]
    D --> D1["プログラミングエラー<br/>(null参照, 型エラー)"]
    D --> D2["インフラ障害<br/>(ディスク枯渇等)"]
    D --> D3["依存サービスの永続的障害"]
```

| エラーの種類 | 例 | 適切な対応 |
|---|---|---|
| バリデーションエラー | 不正なメールアドレス | 400系レスポンスでフィールド単位のエラーを返す |
| ビジネスロジックエラー | 在庫切れ、残高不足 | 409 or 422 でドメイン固有のエラーコードを返す |
| 認証・認可エラー | トークン期限切れ | 401 / 403 で明確に区別する |
| 一時的な外部障害 | DB接続タイムアウト | リトライ（指数バックオフ）→ 503 Service Unavailable |
| プログラミングエラー | null参照、配列の範囲外 | ログに詳細を記録、500で汎用メッセージを返す |

### エラー伝播のモデル

言語・フレームワークによってエラーの伝播モデルが根本的に異なる。

| モデル | 言語/環境 | 特徴 |
|---|---|---|
| 例外（Exception） | JavaScript, Python, Java | `throw`で投げて`try-catch`で捕まえる。暗黙的に伝播する |
| 戻り値（Error as Value） | Go | 関数が`(result, error)`を返す。明示的にチェックする |
| Result型 | Rust, TypeScript(Effect等) | 型システムでエラーハンドリングを強制する |


### エラーレスポンスの設計

ユーザー向けのレスポンスと開発者向けのログは**情報量を分離**する。

```mermaid
flowchart LR
    E["エラー発生"] --> S{"エラーの種類"}
    S -->|クライアント起因| R1["4xx + 具体的なメッセージ<br/>(何が間違っているか)"]
    S -->|サーバー起因| R2["5xx + 汎用メッセージ<br/>(内部情報は隠す)"]
    E --> L["ログ<br/>スタックトレース<br/>リクエストID<br/>コンテキスト情報"]
```

## 他の仕組みとどう関係するか

- **下位レイヤーとの関係:**
  - [[HTTP-HTTPS]] — HTTPステータスコードはエラーハンドリングの「共通語彙」。4xx（クライアントエラー）と5xx（サーバーエラー）の区別が、リトライ戦略やアラート設定の基盤になる
  - [[TCP-IP]] — 接続タイムアウトやコネクションリセットなど、ネットワークレベルのエラーはアプリケーション層で適切にハンドリングする必要がある

- **同レイヤーとの関係:**
  - [[ルーティングとミドルウェア]] — エラーハンドリングミドルウェアはミドルウェアチェーンの最外層に配置し、下位で発生した例外を一括処理する。[[玉ねぎモデル]]の最も外側の層
  - [[認証と認可]] — 認証エラー（401）と認可エラー（403）は明確に区別する。混同するとセキュリティ上の情報漏洩（リソースの存在を示唆）やデバッグの困難さを招く
  - [[API設計-REST-GraphQL]] — RESTではHTTPステータスコードでエラーを表現し、GraphQLでは`errors`配列で表現する。APIのエラーレスポンス形式はクライアント開発者の体験を左右する
  - [[バリデーション]] — バリデーションエラーはエラーハンドリングの最も頻出するケース。フィールド単位の構造化されたエラーレスポンスが求められる

- **上位レイヤーとの関係:**
  - [[Layer5-パフォーマンス/_index|パフォーマンス]] — リトライ戦略（指数バックオフ）、サーキットブレーカー、タイムアウト設定は信頼性の根幹。エラーの発生率はモニタリング・オブザーバビリティの重要なシグナル
  - [[Layer6-セキュリティ/_index|セキュリティ]] — スタックトレースやDB情報をエラーレスポンスに含めると、攻撃者に内部構造を教えることになる。本番ではエラーの詳細を隠蔽し、ログにのみ記録する
  - [[Layer7-設計アーキテクチャ/_index|設計・アーキテクチャ]] — エラーハンドリングは横断的関心事であり、レイヤードアーキテクチャでは各層の責務に応じたエラー変換が必要

## 誤解されやすいポイント

1. **「try-catchで囲めばエラーハンドリングできている」という誤解**
   エラーを捕まえることと、エラーに適切に対応することは別。`catch`ブロックで`console.log(err)`だけ書いて処理を続行するのは「エラーの握りつぶし」であり、最悪のアンチパターン。捕まえたエラーに対して、リトライ・[[フォールバックとグレースフルデグラデーション|フォールバック]]・ユーザーへの通知・処理の中断のいずれかを行わなければ意味がない。

2. **「全ての例外をキャッチすべき」という誤解**
   プログラミングエラー（null参照、型エラー）を回復可能エラーと同じように`catch`して握りつぶすと、バグが隠蔽される。回復不能なエラーはクラッシュさせてログに残し、プロセスマネージャ（PM2、systemd等）に再起動させるのが正しい。

3. **「エラーメッセージは詳細であるほど良い」という誤解**
   ユーザー向けのレスポンスにスタックトレースやSQLクエリを含めるのはセキュリティリスク。**ユーザーには行動指針**（「しばらく待ってから再試行してください」）を、**ログには原因特定に必要な情報**（スタックトレース、リクエストID、入力値）を記録するのが正しい分離。

4. **「HTTPステータスコード 500 を返せばサーバーエラーの処理は完了」という誤解**
   500を返すだけでは、運用チームがエラーの内容を知ることができない。リクエストID（Correlation ID）を生成してレスポンスとログの両方に含め、ログにはエラーの詳細・リクエストコンテキスト・発生箇所を記録すること。

5. **「Goのerrorは面倒だから `_` で無視する」という誤解**
   Goの明示的なエラーハンドリングは冗長に見えるが、エラーが暗黙的に伝播しないことが利点。`_`でエラーを無視すると、例外を握りつぶすのと同じ問題が発生する。Goでは`fmt.Errorf("コンテキスト: %w", err)`でエラーをラップし、呼び出し元に文脈を伝える。

## 設計のベストプラクティス

### 推奨パターン

- **エラーハンドリングを集約する** — 各ハンドラで個別にtry-catchするのではなく、ミドルウェアまたはフレームワークのエラーハンドリング機構で一括処理する
- **構造化されたエラーレスポンスを返す** — `{ error: { code: "VALIDATION_ERROR", message: "...", details: [...] } }` のように、機械的に処理可能な形式にする
- **リクエストIDで追跡可能にする** — 全リクエストにユニークIDを付与し、レスポンスヘッダとログの両方に含める。障害時の調査速度が劇的に改善する
- **エラーにコンテキストを付与してラップする** — 「何をしている最中に」「どの入力に対して」エラーが起きたかを伝播する
- **リトライには指数バックオフを使う** — 固定間隔のリトライは障害中のサービスに負荷をかける。1s → 2s → 4s → 8s のように間隔を広げ、ジッター（ランダムな揺らぎ）を加える

### アンチパターン

- **エラーの握りつぶし** — `catch (e) {}` で何もしない。障害が見えなくなり、原因不明のデータ不整合を引き起こす
- **全てを500で返す** — クライアント起因のエラー（400系）とサーバー起因のエラー（500系）を区別しないと、リトライ戦略もアラートも正しく機能しない
- **エラーメッセージにユーザー入力をそのまま含める** — XSS（Reflected XSS）の原因になりうる。入力値はサニタイズしてからエラーメッセージに含める
- **同期処理と非同期処理でエラーハンドリングを統一しない** — Node.js 15 以降は未処理 Promise rejection はデフォルトで throw 扱いとなり、`uncaughtException` で捕捉しなければプロセスがクラッシュする（旧: 警告のみ）。古い記事のサンプルコードをそのまま流用すると本番で予期せぬクラッシュを招く

## AIエージェントとの協働

> このトピックでAIコーディングエージェント（Claude Code, Copilot, Cursor 等）と協働するための観点。
> エラー型階層・ミドルウェア・リトライ実装は AI に任せやすい一方、**「握りつぶし (`catch (e) {}`)」「フォールバック値の捏造 (`return []`)」「スタックトレースのレスポンス露出」** が頻出事故。レビューも `/review-ai-code` で横断アンチパターン照合に任せられる。

### AIに任せられる部分 / 人間が判断すべき部分

| タスク種類 | 任せ方（実装/レビュー） | 人間の関与 |
|---|---|---|
| カスタムエラークラス階層の設計 | AI に複数案を出させる | エラー型と HTTP ステータスのマッピング、`code` 文字列の語彙はビジネス要件で決める |
| エラーハンドリングミドルウェア / `rescue_from` 実装 | AI 実装、`/review-ai-code` でレビュー | 何をログ送信し、何を Sentry に送るか、PII（個人情報）をどうマスクするかは要件で判断 |
| リトライ・指数バックオフ実装 | AI に任せる | リトライ対象（4xx は除く）、最大試行回数、ジッター幅、サーキットブレーカー閾値はサービス特性で決める |
| エラーレスポンス JSON フォーマット | AI が RFC 9457 準拠の素案 | `details` の構造、`requestId` のヘッダ名、エラーコード命名規則はチーム合意が必要 |
| 既存コードの try-catch リファクタ | AI が集約案を提案 | どのレイヤーで catch すべきか（境界ファイル / ハンドラ / リポジトリ）は設計判断 |
| 回復可能 / 不能の分類 | AI に分類させる | 「これは握りつぶして良いか」の最終判断は人間。ログだけ残してフォールバックして良いケースは限定的 |

### AI生成コードのレビュー観点（このトピック固有）

AI生成のエラーハンドリングコードを受け取ったとき、最低限ここを見る。

1. **握りつぶしとフォールバック値の捏造** — `catch (e) {}` で何もしない、`catch { return [] }` で空配列を返す、`catch { return null }` でデフォルト値を返す等、**エラーを隠蔽してデータ不整合を引き起こすパターン**になっていないか。エラーは原則として呼び出し元に伝播させ、ビジネス的に「失敗をスキップして良い」場合のみログ + 既知のフォールバック値を返す
2. **スタックトレース・SQL・内部パスのレスポンス露出** — `err.stack` `err.message`（DB原文エラー含む可能性）`err.sql` をそのまま JSON に含めていないか。本番ではエラーレスポンスは **汎用メッセージ + リクエストID** に統一し、詳細はログのみ。攻撃者へのヒント漏洩・依存ライブラリのバージョン特定を防ぐ
3. **HTTPステータスコードの誤用とリトライ可能性の欠落** — 全エラーを 500 で返していないか。バリデーションエラー（422）、認証エラー（401）、認可エラー（403）、競合（409）、依存外部障害（503）を区別しないと、クライアント側のリトライ戦略が機能しない。`Retry-After` ヘッダの付与も忘れがち

### 効くプロンプトの型

このトピックに関する実装をAIに依頼するとき、コンテキストとして渡すべき情報・制約・成功基準のテンプレ。

```
# 前提（プロジェクトの状況・既存のコード規約）
- フレームワーク: Express 4 / Chi v5 / Laravel 11 / Rails 7.1 など
- 既存のエラー型階層: AppError / ValidationError / NotFoundError ...
- ログ送信先: Sentry / Datadog / CloudWatch
- PII マスク方針: email は domain のみ残す、credit_card は完全マスク
- リクエストID 付与: X-Request-ID ヘッダ + ログ tag

# やってほしいこと
- 「{要件}」のエラーハンドリング機構を実装
- エラー型階層の追加とミドルウェアでの変換ロジックを含める

# 守ってほしい制約（このトピック固有のもの）
- catch (e) {} やフォールバック値捏造 (return [] / return null) は禁止
- レスポンスにスタックトレース・SQL・内部パスを含めない（汎用メッセージ + requestId）
- 詳細は構造化ログ (JSON) で stdout に出力（PII はマスク）
- HTTPステータスはエラー型に応じて分岐（400/401/403/404/409/422/429/500/503）
- 5xx には Retry-After ヘッダを付与（指数バックオフ用）
- エラーコードは UPPER_SNAKE_CASE で語彙集に登録
- 集約エラーハンドラはチェーン最外層、各ハンドラは throw / raise するだけ

# 完了の判断基準
- 全エラーが集約ハンドラに到達し、レスポンスフォーマットが統一されている
- ログに requestId・コード・パス・ユーザID（あれば）が必ず含まれる
- スタックトレースが本番レスポンスに含まれない
- 4xx と 5xx の区別が正しく、クライアント側でリトライ判定できる
```

### AI実装のアンチパターン

LLM生成コードで頻出する過剰設計・誤用パターン。レビュー時の照合表として使う。

| アンチパターン | なぜ問題か | レビュー観点 / 対策 |
|---|---|---|
| `catch (e) {}` でエラー握りつぶし | 障害が見えなくなり、原因不明のデータ不整合を引き起こす | catch で何もしないのは禁止。最低でも `logger.error` + 再 throw |
| `catch { return [] }` `catch { return null }` でフォールバック値捏造 | エラーが正常系として処理され、上位レイヤーが不正データで動く | エラーは呼び出し元に伝播。フォールバックは「失敗をスキップして良い」要件のみ、ログ + 既知のデフォルト値で明示 |
| 全関数に try-catch を直書き | エラー処理の責務が分散し、フォーマットが不統一に | フレームワーク標準の集約機構（Express 4 引数 ms / Laravel `withExceptions` / Rails `rescue_from`）に集約 |
| 過剰な防御的コーディング（あらゆる引数に null チェック） | 可読性が壊滅、信頼境界が曖昧に | 外部入力（HTTP body・DB結果のオプショナル）のみバリデーション。内部関数間ではスキーマと型を信頼 |
| スタックトレース・SQL・内部パスをレスポンスに含める | 内部構造漏洩、攻撃者に依存ライブラリ・ファイル構造を教える | 本番は汎用メッセージ + requestId。詳細はログのみ |
| 全エラーを 500 で返す | クライアントがリトライ戦略を立てられない、アラートも誤発火 | エラー型 → HTTPステータスのマッピング表を作り、4xx/5xx を正しく分ける |
| ユーザー入力をそのままエラーメッセージに含める | Reflected XSS の温床、ログ injection の原因 | 入力値はサニタイズしてから含めるか、ID 参照のみログに残す |
| 同期 try-catch で Promise/await を捕まえようとする | Node.js では unhandled rejection として漏れ、プロセスクラッシュ | `async function` 内で try-catch、または `.catch()` で明示的に捕捉 |
| リトライを全エラーで実施 | 4xx（クライアント起因）でも無限リトライし、サーバ負荷増大 | 5xx と一部の冪等な 4xx（429 Too Many Requests）のみリトライ。指数バックオフ + ジッター + 最大試行回数 |
| トランザクション内で例外をキャッチして握りつぶし | コミットが走り、不整合データが永続化される | トランザクション内のエラーは必ず再 throw、または明示的にロールバック |

→ レイヤー横断のアンチパターン索引: [[_anti-patterns/_index|AIアンチパターン索引]] / [[_anti-patterns/レイヤー別/Layer4-Backend|Layer 4 Backend アンチパターン集]]

### Express（Node.js）— エラーハンドリングミドルウェア

> **Express 4 と 5 の重要な挙動差:**
> - **Express 4.x**: ハンドラ内の **同期 throw** はエラーミドルウェアに到達するが、**`async function` 内の throw（rejected Promise）は到達しない** — unhandled rejection になりプロセスがクラッシュ・ハングする。`async` ハンドラでは明示的に `try-catch` するか `express-async-errors` パッケージを導入する必要がある
> - **Express 5.0 (2024-10-15 GA)**: async ハンドラの reject も自動的にエラーミドルウェアに繋がる。下記の例は Express 5 ならそのまま動作するが、Express 4 で動かす場合は `app.post('/orders', asyncHandler(async (req, res) => { ... }))` のようなラップが必要

```javascript
const express = require('express');
const crypto = require('crypto');
const app = express();
app.use(express.json());

// カスタムエラークラス
class AppError extends Error {
  constructor(statusCode, code, message) {
    super(message);
    this.statusCode = statusCode;
    this.code = code;
  }
}

// リクエストIDミドルウェア
app.use((req, res, next) => {
  req.id = crypto.randomUUID();
  res.setHeader('X-Request-ID', req.id);
  next();
});

// ビジネスロジック — エラーはthrowするだけ
app.post('/orders', (req, res) => {
  const { productId, quantity } = req.body;
  if (!productId || !quantity) {
    throw new AppError(422, 'VALIDATION_ERROR', 'productId and quantity are required');
  }
  // 在庫チェック（デモ）
  const stock = 5;
  if (quantity > stock) {
    throw new AppError(409, 'INSUFFICIENT_STOCK', `Requested ${quantity}, but only ${stock} available`);
  }
  res.status(201).json({ orderId: 'order-123', productId, quantity });
});

// 存在しないリソース
app.get('/users/:id', (req, res) => {
  const user = null; // DBから見つからない想定
  if (!user) {
    throw new AppError(404, 'USER_NOT_FOUND', `User ${req.params.id} not found`);
  }
  res.json(user);
});

// 集約エラーハンドリングミドルウェア（4引数で定義）
app.use((err, req, res, _next) => {
  // 既知のアプリケーションエラー
  if (err instanceof AppError) {
    console.error(JSON.stringify({
      requestId: req.id, code: err.code,
      message: err.message, path: req.path,
    }));
    return res.status(err.statusCode).json({
      error: { code: err.code, message: err.message, requestId: req.id },
    });
  }

  // 未知のエラー（プログラミングエラー等）
  console.error(JSON.stringify({
    requestId: req.id, message: err.message,
    stack: err.stack, path: req.path,
  }));
  res.status(500).json({
    error: {
      code: 'INTERNAL_ERROR',
      message: 'An unexpected error occurred. Please try again later.',
      requestId: req.id,
    },
  });
});

app.listen(3000);
```

### Go（Chi）— エラーをハンドラの戻り値で扱うパターン

```go
package main

import (
	"encoding/json"
	"fmt"
	"log/slog"
	"net/http"

	"github.com/go-chi/chi/v5"
	"github.com/google/uuid"
)

// アプリケーションエラー型
type AppError struct {
	StatusCode int    `json:"-"`
	Code       string `json:"code"`
	Message    string `json:"message"`
}

func (e *AppError) Error() string {
	return fmt.Sprintf("%s: %s", e.Code, e.Message)
}

// エラーを返せるハンドラ型
type AppHandler func(w http.ResponseWriter, r *http.Request) error

// ハンドラをラップしてエラーを集約処理する
func handleErrors(h AppHandler) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		err := h(w, r)
		if err == nil {
			return
		}
		requestID := r.Header.Get("X-Request-ID")

		// AppErrorの場合はクライアント向けメッセージを返す
		if appErr, ok := err.(*AppError); ok {
			slog.Error("app error",
				"request_id", requestID,
				"code", appErr.Code,
				"message", appErr.Message,
				"path", r.URL.Path,
			)
			w.Header().Set("Content-Type", "application/json")
			w.WriteHeader(appErr.StatusCode)
			json.NewEncoder(w).Encode(map[string]any{
				"error": map[string]any{
					"code": appErr.Code, "message": appErr.Message,
					"requestId": requestID,
				},
			})
			return
		}

		// 未知のエラー — 詳細はログのみ、レスポンスには汎用メッセージ
		slog.Error("unexpected error",
			"request_id", requestID,
			"error", err.Error(),
			"path", r.URL.Path,
		)
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusInternalServerError)
		json.NewEncoder(w).Encode(map[string]any{
			"error": map[string]any{
				"code":      "INTERNAL_ERROR",
				"message":   "An unexpected error occurred",
				"requestId": requestID,
			},
		})
	}
}

// リクエストIDミドルウェア
func requestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := uuid.New().String()
		r.Header.Set("X-Request-ID", id)
		w.Header().Set("X-Request-ID", id)
		next.ServeHTTP(w, r)
	})
}

func main() {
	r := chi.NewRouter()
	r.Use(requestID)

	r.Get("/users/{id}", handleErrors(getUser))
	r.Post("/orders", handleErrors(createOrder))

	http.ListenAndServe(":3000", r)
}

func getUser(w http.ResponseWriter, r *http.Request) error {
	id := chi.URLParam(r, "id")
	// DBから検索（デモ: 常に見つからない）
	return &AppError{
		StatusCode: http.StatusNotFound,
		Code:       "USER_NOT_FOUND",
		Message:    fmt.Sprintf("User %s not found", id),
	}
}

func createOrder(w http.ResponseWriter, r *http.Request) error {
	var input struct {
		ProductID string `json:"productId"`
		Quantity  int    `json:"quantity"`
	}
	if err := json.NewDecoder(r.Body).Decode(&input); err != nil {
		return &AppError{
			StatusCode: http.StatusBadRequest,
			Code:       "INVALID_BODY",
			Message:    "Request body must be valid JSON",
		}
	}
	if input.ProductID == "" || input.Quantity <= 0 {
		return &AppError{
			StatusCode: http.StatusUnprocessableEntity,
			Code:       "VALIDATION_ERROR",
			Message:    "productId and positive quantity are required",
		}
	}
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusCreated)
	json.NewEncoder(w).Encode(map[string]any{
		"orderId": "order-123", "productId": input.ProductID, "quantity": input.Quantity,
	})
	return nil
}
```

### リトライ戦略 — 指数バックオフ

```javascript
// 4xx と 5xx を別の例外型で表現し、catch 側で「リトライするか」を分岐できるようにする
class ClientError extends Error {
  constructor(status) { super(`Client error: ${status}`); this.status = status; }
}
class ServerError extends Error {
  constructor(status) { super(`Server error: ${status}`); this.status = status; }
}

async function fetchWithRetry(url, options = {}, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      const res = await fetch(url, options);
      // 4xx はリトライしない（クライアント起因）— 専用例外で投げ、catch 側で再 throw する
      if (res.status >= 400 && res.status < 500) {
        throw new ClientError(res.status);
      }
      // 5xx はリトライ対象
      if (res.status >= 500) {
        throw new ServerError(res.status);
      }
      return res;
    } catch (err) {
      // ClientError（4xx）は即座に再 throw してループを抜ける
      if (err instanceof ClientError) throw err;
      // 最終試行も失敗なら諦めて throw
      if (attempt === maxRetries) throw err;
      // 5xx・ネットワークエラーのみここに到達 → 指数バックオフ + ジッター
      const delay = Math.min(1000 * 2 ** attempt, 10000);
      const jitter = delay * 0.5 * Math.random();
      await new Promise(r => setTimeout(r, delay + jitter));
    }
  }
}
```

> [!note]- 解答の指針
>
> > [!info] 用語ミニ辞典
> > - **回復可能エラー (Recoverable):** バリデーションエラー・在庫切れ・一時的な外部障害など、適切な対応で続行可能なエラー。HTTPステータスは 4xx 系（クライアント起因）または 503（一時的な依存障害）を返す
> > - **回復不能エラー (Unrecoverable):** null参照・型エラーなどのプログラミングエラー、ディスク枯渇などのインフラ障害。HTTPステータスは 500 で汎用メッセージを返し、ログに詳細を記録、プロセスマネージャに再起動させる
> > - **リクエストID (Correlation ID / X-Request-ID):** リクエスト1件ごとにユニークに付与する識別子。レスポンスヘッダとログ両方に含めることで、ユーザーから「エラーが出た」と報告されたときに該当ログを瞬時に引ける
> > - **指数バックオフ (Exponential Backoff):** リトライ間隔を 1s → 2s → 4s → 8s と指数的に広げる方式。固定間隔だと障害中のサービスに集中負荷をかけて回復を妨げる。さらに**ジッター（ランダム揺らぎ）** を加えて全クライアントが同時にリトライしないようにする
> > - **サーキットブレーカー (Circuit Breaker):** 一定時間内のエラー率が閾値を超えると、リトライ自体を一時的に止めて即座にエラーを返すパターン。障害中の依存サービスへの無駄な負荷を遮断する
> > - **エラー握りつぶし (Swallow):** `catch (e) {}` のように、捕まえたエラーに何もしないこと。障害がログに残らず、データ不整合・ユーザー影響が見えなくなる「最悪のアンチパターン」
> > - **構造化ログ (Structured Logging):** プレーンテキストでなく JSON 形式で `{requestId, level, message, ...}` を出力するログ。検索・集計・アラート設定が容易
> > - **PII (Personally Identifiable Information):** 個人を特定可能な情報（メール・電話番号・クレジットカード番号等）。ログに含める場合はマスクが必要（GDPR・個人情報保護法）
> > - **冪等 (Idempotent):** 同じ操作を何度実行しても結果が同じになる性質。HTTP の GET / PUT / DELETE は冪等で、リトライしても安全。POST は冪等でないため、リトライにはアプリ側の冪等キーが必要
>
> 1. レスポンスとログの情報量分離とは、**ユーザーには「次に何をすべきか」だけを返し、開発者には「なぜ起きたか」の詳細を残す** こと。具体的には、レスポンスは `{error: {code, message, requestId}}` のように汎用メッセージ + リクエストIDのみ、ログは構造化ログでスタックトレース・入力値（PIIマスク後）・コンテキスト・発生箇所を残す。スタックトレースをレスポンスに含めると (a) **使用ライブラリとバージョン**（依存脆弱性スキャンの的になる）、(b) **ファイル構造・モジュール名**（攻撃面の特定）、(c) **DB スキーマ・SQL クエリ**（SQL インジェクション戦略のヒント）が漏洩する。さらに 500 エラーで「stack に email が含まれる」など PII 漏洩経路にもなりうる。本番ではエラー詳細は **必ずサーバ側のログのみに残し**、レスポンスは行動指針のみに統一する
> 2. `catch (e) {}` はエラーが起きたという事実を**消し去る**ため、(a) **障害が監視に上がらない**（例: DB 接続失敗が握りつぶされ、空配列が返り、ユーザーには「データなし」と表示される。実際は全データがあるのに）、(b) **データ不整合の典型例**: トランザクション内で「在庫を減らす」と「注文を作る」の片方が失敗したとき、前者の例外を握りつぶすと「在庫減 + 注文なし」または「在庫据え置き + 注文あり」のいずれかで永続化され、業務的に矛盾、(c) **デバッグ不能**: 障害が起きてから何日も経ってデータ不整合が発覚し、ログにも痕跡がない。原則は **「捕まえたなら何かをする」**：再 throw する、ログに残す、リトライする、フォールバック値を**意図的に**返す、のいずれか。「とりあえず落ちないように」で握りつぶすのが最悪
> 3. AI生成コードの問題点（最低限以下を指摘できれば本文を理解している）:
>     - **エラーレスポンスにスタックトレース・SQL を含めている (`stack: err.stack, sql: err.sql`)** — 内部構造漏洩の典型。本番では汎用メッセージ + requestId のみ
>     - **全エラーを 500 で返している** — 注文が見つからない（404）も、無効な ID 形式（400）も、外部決済プロバイダの一時障害（503）も全部 500 になる。クライアントがリトライ判断できない
>     - **`catch (e) { /* すぐリトライ */ }` でエラー握りつぶし** — `fetchPaymentStatusWithRetry` 内のリトライ catch が `e` をログにも残さない。10回失敗の理由が一切残らないためデバッグ不能
>     - **指数バックオフがない（固定間隔リトライ）** — `for (let i = 0; i < 10; i++)` で待機なしに即座に10回連打。障害中のサービスに集中負荷をかけて回復を妨げる
>     - **ジッターがない** — 全クライアントが同時にリトライするとサンダリングハード問題で外部サービスが二次障害を起こす
>     - **4xx でもリトライしている** — 401/403/404 はリトライしても永久に成功しないため、無駄な負荷とレスポンス遅延を生む。リトライ対象は 5xx と 408/429 などに限定すべき
>     - **リトライ回数が多すぎる (10回)** — 通常は 3〜5 回が妥当。10回 × 指数バックオフだと最終待機時間が分単位になり、リクエストがタイムアウトする
>     - **最終的にエラー時 `{status: 'unknown'}` を返している** — フォールバック値の捏造。呼び出し元が「決済済み」と誤認するリスク。エラーを呼び出し元に伝播させ、上位で判断すべき
>     - **`db.query` の戻り値を `order` としてそのまま使っているが null チェックがない** — 注文が見つからない場合、`order.payment_id` で TypeError が発生し 500 になる。本来は `NotFoundError(404)` で返すべき
>     - **リクエストID の生成・ログ・レスポンスへの含有がない** — 障害発生時にログとユーザー報告を紐付けられない
>     - **`Retry-After` ヘッダの付与がない** — クライアントがリトライタイミングを判断できない

## 学習メモ

- Goの`fmt.Errorf("context: %w", err)`によるエラーラッピングと`errors.Is()`/`errors.As()`の使い分けは重要
- Node.jsではunhandled rejectionがプロセスクラッシュの原因になるため、`process.on('unhandledRejection')`の設定を忘れない
- エラーレスポンスのフォーマットは一度決めたら変えにくいため、プロジェクト初期に決定すべき設計判断
