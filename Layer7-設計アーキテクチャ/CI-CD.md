# CI/CD

> **一言で言うと:** 「手動デプロイが怖い」問題を解決する。自動テスト→自動ビルド→自動デプロイのパイプラインにより、小さく頻繁にリリースすることでリスクを下げる。

## 3分で全体像

- **何を解決する技術か:** 「本番デプロイが恐怖のイベントになる」「自分の環境では動く問題が頻発」「品質保証が属人化する」というリリースサイクルの慢性問題を、自動テスト→ビルド→デプロイのパイプラインで構造的に止める
- **代表的な使用シーン:** GitHub への push 時の自動テスト・リント・型チェック・セキュリティスキャン、PR 時のビルド検証、main マージ時のステージング自動デプロイ、tag push での本番リリース、フィーチャーフラグと組み合わせたカナリア / ブルーグリーンデプロイ、依存ライブラリの自動更新（Dependabot / Renovate）
- **これだけは覚える3つ:**
    1. **「ツール導入 = CI/CD」ではない** — GitHub Actions / Jenkins を入れただけでは CI にならない。CI の本質は**開発者が頻繁に（最低 1 日 1 回）コードを統合する文化**。長期ブランチ・週末 PR・大規模リファクタの一括マージはどんなツールでも統合地獄を起こす
    2. **デプロイ頻度を上げるとリスクは「下がる」** — DORA 調査が実証する直感に反する事実。1 回のデプロイに含まれる変更が小さいほど、原因特定とロールバックが容易になる。**怖いから頻度を下げる**は逆方向の最適化
    3. **デプロイとリリースを分離する** — フィーチャーフラグで「コードを本番に置くこと（デプロイ）」と「ユーザーに機能を見せること（リリース）」を切り離す。これにより**リスクの大きい変更も日常的にデプロイ**でき、機能の有効化はランタイムで制御できる
- **AIに任せやすいか:** **任せやすい** — GitHub Actions / GitLab CI / CircleCI のワークフロー YAML、Dockerfile、デプロイスクリプトは AI が高品質に書ける。テンプレートが豊富で、サービスごとの違いも公式ドキュメントベースの定型作業。一方で **「シークレット管理戦略」「環境分離方針」「デプロイ戦略の選択（カナリア / ブルーグリーン）」** は組織の本番運用方針を反映するため人間判断が要る。AI は**シークレットをハードコードする / 全テストを 1 ジョブで直列実行する / `--no-verify` で hook を回避する**バイアスがあり、生成された YAML の**シークレット参照箇所**と**ジョブ並列度**は必ず疑う
- **詰まったらここを読む:** [[テスト戦略]] / [[Docker]] / [[モニタリング]] / [[サプライチェーンセキュリティ]]

## なぜ必要か

ソフトウェアは書いただけでは価値がない。ユーザーの手に届いて初めて価値になる。CI/CD（継続的インテグレーション / 継続的デリバリー・デプロイ）がなければ:

- **「本番へのデプロイが恐怖のイベントになる」** — 手動デプロイは手順書の1行飛ばしで障害が起きる。デプロイ頻度が下がり、1回のリリースに含まれる変更が巨大になり、何が原因で壊れたか特定できなくなる悪循環
- **「自分の環境では動く」問題が頻発する** — 開発者ごとに異なる環境でテストし、統合するのは本番デプロイ直前。そこで初めて互いのコードが衝突することに気づく
- **品質保証が属人化する** — 「この手順を知っているのはAさんだけ」「金曜のデプロイはBさんがいないとできない」という状態になり、チームのボトルネックが生まれる
- **修正のリードタイムが長くなる** — バグを見つけてから修正が本番に反映されるまでに数日〜数週間かかると、ユーザーの信頼を失い、ビジネス機会を逃す

## どの問題を解決するか

### CI（Continuous Integration — 継続的インテグレーション）

**問題:** 複数の開発者が独立して作業し、統合を後回しにすると「統合地獄（Integration Hell）」が発生する。ブランチが長期間分岐しているほど、マージ時のコンフリクトと予期しない不具合が増大する。

**解決方法:**
- 開発者は少なくとも1日1回、変更をメインブランチに統合する
- 統合のたびに自動でビルド・テストが実行される
- テストが失敗したら即座に修正する（壊れたビルドの放置は最悪のプラクティス）

### CD — 継続的デリバリー（Continuous Delivery）

**問題:** コードが統合されてもリリースまでの手動作業（ビルド、ステージング環境へのデプロイ、承認フロー）に時間がかかり、リリース頻度が下がる。

**解決方法:**
- ビルド・テスト・ステージングへのデプロイまでを自動化する
- 本番デプロイは**ボタン1つでいつでも実行可能**な状態を維持する
- 本番へのデプロイ判断は人間が行う（ビジネス上のタイミング等）

### CD — 継続的デプロイ（Continuous Deployment）

**問題:** 継続的デリバリーでも、本番デプロイのボタンを押す判断が属人的になりがち。

**解決方法:**
- テストに全て合格した変更は**自動的に本番環境へデプロイされる**
- 最も成熟した形態であり、強固なテスト基盤と[[モニタリング|モニタリング・オブザーバビリティ]]が前提条件

```mermaid
graph LR
    DEV["開発者が<br/>コードをpush"] --> CI["CI<br/>ビルド＋テスト"]
    CI -->|"失敗"| FIX["即座に修正"]
    CI -->|"成功"| STAGE["ステージングに<br/>自動デプロイ"]
    STAGE --> APPROVAL{"承認"}
    APPROVAL -->|"継続的デリバリー<br/>手動承認"| PROD["本番デプロイ"]
    APPROVAL -->|"継続的デプロイ<br/>自動"| PROD

    style CI fill:#ddf,stroke:#333

    style PROD fill:#ffd,stroke:#333
```

## 他の仕組みとどう関係するか

- **下位レイヤーとの関係:**
  - [[Docker|コンテナ]] — CI/CDパイプラインの実行環境としてコンテナが標準。ビルド環境の再現性を保証し「CIでは通るのにローカルでは通らない」問題を解消する
  - [[IaCとクラウドインフラ管理|IaC（Infrastructure as Code）]] — インフラの構成をコードで宣言的に管理し、CI/CDパイプラインに組み込むことでインフラ変更もコードと同じレビュー・デプロイフローに乗せられる。[[AWS-CDKのコンストラクトモデル|AWS CDK]] を使えば TypeScript 等の汎用言語でインフラを定義し、通常のテストフレームワークで検証できる
  - [[Linux基本操作]] — CI環境のほぼ全てがLinux。シェルスクリプトの読み書き、権限管理、環境変数の扱いが必須
  - [[RDB]] — マイグレーションの自動実行をCI/CDパイプラインに組み込む。[[マイグレーション]]のテストもCIで自動化すべき対象
  - [[バリデーション]] — 静的解析（リンター、型チェック）をCIで自動実行し、コードレビュー前に機械的なチェックを完了させる

- **同レイヤーとの関係:**
  - [[テスト戦略]] — CIの価値はテストの質に完全に依存する。テストが不十分なCIは「グリーンのバッジが付いた壊れたコード」を量産する。テストピラミッドの各層をCIのどの段階で実行するかの設計が重要
  - [[モノリスvsマイクロサービス]] — マイクロサービスでは各サービスに独立したCI/CDパイプラインが必要。パイプラインの数 = サービスの数になるため、パイプライン自体のテンプレート化・標準化が運用の鍵
  - [[関心の分離]] — CI/CDパイプライン自体にも関心の分離を適用する。ビルド・テスト・デプロイの各ステージを独立させ、再利用可能にする
  - [[SOLID原則]] — パイプラインの設計にOCPを適用。新しいチェック（セキュリティスキャン等）を追加する際に既存のパイプライン定義を修正しなくて済む構造にする

- **上位レイヤーとの関係:**
  - 最上位レイヤーのため直接の上位はない。ただしCI/CDはビジネスのリリースサイクルやチームの働き方に直結するため、技術を超えた組織的な判断が伴う

## 誤解されやすいポイント

### 1. 「CI/CDツールを導入すれば CI/CD が実現する」わけではない

GitHub Actions や Jenkins を導入しただけでは CI/CD にならない。CI の本質は**開発者が頻繁にコードを統合する文化**であり、ツールはそれを支援する手段にすぎない。ブランチが何週間も分岐したまま放置されていれば、どんなに高機能なCIツールを使っても統合地獄は避けられない。

### 2. 「テストが全部グリーンなら品質は保証されている」わけではない

CIのテストはあくまで「書いたテストが通った」ことを証明するだけ。テスト自体の品質が低ければ（カバレッジが不十分、エッジケースが未考慮、モックが過剰で実態と乖離）、グリーンのパイプラインは偽りの安心感を与える。[[テスト戦略]]の設計とセットで考える必要がある。

### 3. 「デプロイ頻度を上げるとリスクが増える」は逆

直感に反するが、デプロイ頻度が高いほどリスクは**下がる**。1回のデプロイに含まれる変更が小さいため、問題の原因特定とロールバックが容易になる。DORA（DevOps Research and Assessment、2018年に Google Cloud が買収）の調査で、デプロイ頻度・変更リードタイム・障害復旧時間・変更失敗率の4指標でデリバリーパフォーマンスを測定でき、高パフォーマンスチームはこれら全てが優れていることが実証されている。

### 4. 「CI/CD パイプラインは一度作ったら完成」ではない

パイプラインはプロダクトと同様に継続的にメンテナンスが必要。テストの追加、ビルド時間の最適化、セキュリティスキャンの導入、依存ライブラリの更新チェックなど、プロジェクトの成長に合わせて進化させる。パイプラインの実行時間が長くなりすぎると開発者がCIの結果を待たずにマージするようになり、CIの価値が損なわれる。

## 設計のベストプラクティス

### 推奨パターン

**1. パイプラインを高速に保つ**

CIの実行時間は10分以内を目標にする。これを超えるとフィードバックループが遅くなり、開発者がCIの結果を待たずに次の作業に移る。高速化の手法:
- テストの並列実行
- キャッシュの活用（依存パッケージ、ビルド成果物）
- 変更されたモジュールのみテスト実行（モノレポの場合）

**2. パイプラインの段階的実行**

全てのチェックを直列に実行するのではなく、速いチェックから順に実行する。

```mermaid
graph TD
    PUSH["git push"] --> STAGE1["Stage 1: 高速チェック（〜2分）<br/>リント・型チェック・ユニットテスト"]
    STAGE1 -->|"失敗"| STOP1["即座にフィードバック"]
    STAGE1 -->|"成功"| STAGE2["Stage 2: 中速チェック（〜5分）<br/>インテグレーションテスト・ビルド"]
    STAGE2 -->|"失敗"| STOP2["フィードバック"]
    STAGE2 -->|"成功"| STAGE3["Stage 3: 低速チェック（〜10分）<br/>E2Eテスト・セキュリティスキャン"]
    STAGE3 -->|"成功"| DEPLOY["デプロイ可能"]

    style STAGE1 fill:#dfd,stroke:#333
    style STAGE2 fill:#ddf,stroke:#333
    style STAGE3 fill:#ffd,stroke:#333
```

**3. トランクベース開発（Trunk-Based Development）**

短命なフィーチャーブランチ（1〜2日）を使い、頻繁にメインブランチへマージする。長期ブランチを避けることで統合リスクを最小化する。この戦略が成立するのは Git のブランチが「コミットを指す 1 行のファイル」に過ぎず作成・破棄が極めて軽いためで、マージとリベースのどちらを選ぶか・どこまで履歴を書き換えてよいかの判断基準は [[Gitの内部モデルとブランチ操作]] に整理してある。

**4. デプロイとリリースを分離する**

コードの本番デプロイと、ユーザーへの機能公開を分離する。フィーチャーフラグにより、デプロイ済みのコードの有効/無効をランタイムで制御できる。

### アンチパターン

**1. 壊れたビルドの放置** — 「誰かが直すだろう」でCIの赤を放置すると、チーム全体がCIの結果を無視するようになる。壊れたビルドの修正は最優先タスク。

**2. 手動ステップの混入** — パイプラインの途中に「手動でこのスクリプトを実行」「Slackで承認を依頼」等の手動ステップがあると、自動化の恩恵が半減する。

**3. 環境ごとの設定の散乱** — 開発/ステージング/本番で異なる設定が散在し、環境差異によるバグが発生する。設定は環境変数で注入し、コードは全環境で同一にする。秘密情報を含む `.env` を安全に共有・管理する手段として、暗号化したまま git にコミットできる [[dotenvx]] という選択肢もある。

## AIエージェントとの協働

> このトピックでAIコーディングエージェント（Claude Code, Copilot, Cursor 等）と協働するための観点。
> **「AIに何をどこまで任せ、AIに何をレビューさせ、人間は何を最終判断するか」**を整理する。実装だけでなく**レビューもAIに任せられる**前提で考える（AIコードレビュー観点で横断アンチパターン照合を行う）。

### AIに任せられる部分 / 人間が判断すべき部分

| タスク種類 | 任せ方（実装/レビュー） | 人間の関与 |
|---|---|---|
| GitHub Actions / GitLab CI ワークフロー作成 | **実装もレビューも AI 主導** — Node.js / Python / Go / PHP の典型ジョブ（lint / typecheck / test / build / deploy）は AI が高品質に書く | シークレット参照箇所が `${{ secrets.X }}` 経由になっているか、ハードコードがないかの確認 |
| Dockerfile のマルチステージビルド | **実装もレビューも AI 主導** — `builder` ステージ + `runtime` ステージの典型構成 | 本番イメージサイズ、`USER` 指定、`COPY` の対象範囲のレビュー（[[最小権限の原則]] 準拠） |
| ジョブ並列化・キャッシュ最適化 | **実装は AI 主導** — `actions/cache` や `setup-node` の `cache: 'npm'` は AI が定型化 | 実行時間のボトルネック特定とリソース配分は実測ベースで人間判断 |
| デプロイ戦略の選択 | **AI に複数案** — ローリング / ブルーグリーン / カナリアの実装案を提示させて比較 | **人間が最終判断** — ダウンタイム許容度・インフラコスト・ロールバック要件で選ぶ |
| シークレット管理の方針 | **AI に任せない** — AI は `secrets.X` 構文は書くが、組織のシークレット運用ポリシーは知らない | **完全に人間判断** — Vault / SSM Parameter Store / KMS の選択、回転頻度、アクセス権限 |
| 「壊れたビルドの放置」文化対応 | **AI で代替不可** — 技術的問題ではなく組織文化の問題 | **完全に人間判断** — チームでの優先度合意、CI が赤の時にマージ禁止のルール化 |
| 環境分離の方針（dev / staging / prod） | **AI に基本案** — `if: github.ref == 'refs/heads/main'` のような分岐は定型。**GitHub Actions Environments** を使えば環境別 secrets と承認ゲート（`required reviewers`）を宣言的に組める | **人間が最終判断** — 環境数、承認フロー、コンプライアンス要件で決める。本番 deploy ジョブを Environment に紐付け、production secrets を development から分離するのが現代的なベストプラクティス |

### AI生成コードのレビュー観点（このトピック固有）

AI生成物を受け取ったとき、最低限ここを見る。

1. **シークレットがコードに残っていないか** — AI は動作確認のために `API_KEY: 'sk_test_...'` のように YAML に直書きすることがある。**`secrets.` 参照のみで、リテラルが書かれていないか**を git diff で必ず確認。一度コミットされた機密情報は履歴から完全削除が困難
2. **本番と CI の環境差異がないか** — 「CI では SQLite / 本番は PostgreSQL」「CI ではメモリ DB / 本番は Redis」のような置き換えは、本番でしか発現しないバグを通す。**`services:` で本番同型のコンテナ**を起動するのが基本
3. **`--no-verify` / `git commit` の hook バイパス**が紛れ込んでいないか — AI は hook 失敗時に「回避策として」`--no-verify` を提案することがある。CI 上でも開発ローカルでも、**回避は根本原因解決の機会喪失**。デプロイスクリプトに混入していないか grep で確認

### 効くプロンプトの型

このトピックに関する実装をAIに依頼するとき、コンテキストとして渡すべき情報・制約・成功基準のテンプレ。

```
# 前提（プロジェクトの状況・既存のコード規約）
- スタック: Node.js 22 / TypeScript / pnpm / PostgreSQL 17
- 既存 CI: なし（新規導入）
- デプロイ先: AWS ECS Fargate（本番のみ、ステージングは未構築）
- シークレット管理: GitHub Actions Secrets を使用
- ブランチ戦略: trunk-based（main + 短命 feature ブランチ）

# やってほしいこと
- GitHub Actions のワークフロー作成。push 時に lint / typecheck / unit test、PR 時にこれらに加えて integration test、main マージ時に ECS 自動デプロイ

# 守ってほしい制約（このトピック固有のもの）
- シークレットは `secrets.X` 経由のみ。YAML 内にリテラル禁止
- 高速チェック（lint / typecheck / unit）と低速チェック（integration / e2e）を別ジョブで並列化
- integration test では PostgreSQL 17 を `services:` で起動（本番と同一バージョン）
- ECS デプロイは main への push 時のみ実行（PR では実行しない）
- 失敗時のみ Slack 通知（成功通知は無効）
- pnpm ストアと node_modules を `actions/cache` でキャッシュ

# 完了の判断基準
- PR 作成から CI 完了まで 8 分以内
- 本番デプロイは main マージから 12 分以内に完了
- シークレットがリポジトリ内に一切書かれていない
- 失敗時に Slack に通知される
```

### AI実装のアンチパターン

LLM生成コードで頻出する過剰設計・誤用パターン。レビュー時の照合表として使う。

| アンチパターン | なぜ問題か | レビュー観点 / 対策 |
|---|---|---|
| 全テストを1ジョブで直列実行 | パイプラインの実行時間が長くなり、フィードバックが遅延する | テストを並列化し、段階的に実行する |
| シークレットのハードコード | APIキーやパスワードをパイプライン定義ファイルに直接記述。リポジトリに機密情報が残る | CI/CDプラットフォームのシークレット管理機能を使用する。一度コミットされたら git 履歴から完全削除が困難で、漏洩は確定的 |
| 過剰なパイプライン通知 | 全ステップの成功/失敗をSlackに通知。ノイズで本当に重要な失敗が埋もれる | 失敗時のみ通知。成功はダッシュボードで確認 |
| 本番と異なるCI環境 | CIではSQLiteでテスト、本番はPostgreSQL。環境差異による本番障害が発生する | CI環境を本番に可能な限り近づける（[[Docker|コンテナ]]で同一イメージを使用） |
| `--no-verify` / hook バイパス | pre-commit / pre-push hook の失敗を `--no-verify` で回避する手順が混入。ローカルチェックの意味が消える | hook 失敗は根本原因を直す。AI 生成のスクリプトに `--no-verify` が含まれていないか grep |
| キャッシュキー不適切 | `actions/cache` のキーが固定値で、依存変更後も古いキャッシュが使われる | `hashFiles('**/package-lock.json')` のように依存ファイルのハッシュを含める |
| マイグレーションを CD パイプライン外で手動実行 | 本番デプロイとマイグレーションのタイミングがずれ、新コードが古いスキーマで動く | パイプラインに `npm run migrate` を組み込み、後方互換マイグレーション（カラム追加→デプロイ→旧カラム削除）の順序を守る |
| 失敗時の自動ロールバックなし | 本番デプロイ失敗時の自動戻しがなく、手動で前バージョンを再デプロイする | ECS / Kubernetes の `rollback` 機能を活用、ヘルスチェック失敗で自動ロールバック |
| イメージタグに `latest` のみ使用 | デプロイ時にどのコミットのコードが入っているか追跡不能 | コミット SHA や semver タグを使い、`latest` は補助的に |

→ レイヤー横断のアンチパターン索引: [[_anti-patterns/_index|AIアンチパターン索引]]

## 具体例

### GitHub Actions — 基本的なCI/CDパイプライン

```yaml
# .github/workflows/ci.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  # Stage 1: 高速チェック
  lint-and-typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck

  # Stage 1: ユニットテスト（リントと並列実行）
  unit-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'
      - run: npm ci
      - run: npm test -- --coverage

  # Stage 2: インテグレーションテスト（Stage 1 完了後）
  integration-test:
    needs: [lint-and-typecheck, unit-test]
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_DB: test
          POSTGRES_USER: test
          POSTGRES_PASSWORD: test
        ports:
          - 5432:5432
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: 'npm'
      - run: npm ci
      - run: npm run test:integration
        env:
          DATABASE_URL: postgres://test:test@localhost:5432/test

  # Stage 3: デプロイ（mainブランチへのpush時のみ）
  deploy:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    needs: [integration-test]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to production
        run: ./scripts/deploy.sh
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
```

1. 「デプロイ頻度を上げるとリスクが増える」という直感に反して、実際にはリスクが下がるとされる理由を、DORA メトリクスと「変更の粒度」「原因特定の容易さ」の観点から 30 秒で説明してみよう
2. 「CI が通っているのに本番で予期せぬバグが発生する」という状況には複数の原因がありうる。代表的な原因を 3 つ挙げ、それぞれの対策を答えよ
3. AI が次の GitHub Actions ワークフロー YAML を生成した。本番投入する前に修正すべき問題点を 3 つ以上指摘し、修正方針を答えよ

   name: Deploy

     push:
       branches: [main]

> [!note]- 解答の指針
>
> > [!info] 用語ミニ辞典
> > - **CI（Continuous Integration / 継続的インテグレーション）**: 開発者が頻繁に（最低 1 日 1 回）コードをメインブランチに統合し、その都度自動でビルド・テストを実行する開発プラクティス
> > - **CD（Continuous Delivery / Continuous Deployment）**: Delivery は「いつでも本番デプロイ可能な状態を維持する」、Deployment は「テスト合格次第自動的に本番デプロイする」もの。前者は人間が最終承認、後者は完全自動
> > - **DORA メトリクス**: DevOps Research and Assessment（Google Cloud 傘下）が定義したデリバリーパフォーマンス指標。当初 4 指標（デプロイ頻度・変更リードタイム・障害復旧時間 MTTR・変更失敗率）で、2021 年の State of DevOps Report 以降は **5 指標目「信頼性（Reliability / Operational Performance）」** が追加されている。Accelerate 書籍時代（2018）の 4 指標版が広く知られているが、最新は 5 指標版
> > - **トランクベース開発**: 短命なフィーチャーブランチ（1〜2 日）を使い、頻繁にメインブランチへマージするブランチ戦略。長期ブランチによる統合地獄を避ける
> > - **フィーチャーフラグ**: コードの本番配置と機能のユーザー公開を分離する仕組み。環境変数や設定 DB で機能を有効化／無効化する
> > - **ヘルスチェック**: デプロイ後にアプリケーションが正常に動作しているか確認するエンドポイント。失敗時は自動ロールバック
> > - **シークレット管理**: API キー・パスワード・証明書などの機密情報を、コードに含めず暗号化された専用ストア（AWS Secrets Manager / GitHub Secrets / HashiCorp Vault 等）で管理する仕組み
>
> 1. **理由 1: 変更の粒度が小さくなる**。1 回のデプロイに含まれる変更が小さければ、何かが壊れた時に**原因特定が容易**で、ロールバックも単純。逆に 1 ヶ月に 1 回まとめてリリースすると、含まれる変更が膨大で、どの変更が問題を引き起こしたかの調査に時間がかかる
>
>    **理由 2: デプロイそのものに慣れる**。頻繁にデプロイすれば、デプロイ手順・自動化・モニタリング・ロールバック手順が**日常のオペレーション**として磨かれていく。逆に頻度が低いと「特別なイベント」になり、毎回手順が異なり手動ミスが入る
>
>    **DORA の実証**: DORA メトリクス（デプロイ頻度・変更リードタイム・MTTR・変更失敗率）の調査で、**高パフォーマンスチームは全 4 指標で優れている**ことが実証されている。デプロイ頻度が高いチームは変更失敗率も低い（互いに正の相関）。「頻度を上げる」と「失敗率が下がる」は矛盾せず両立する
>
>    **判断のコツ**: 「デプロイが怖い」と感じるなら、それは**頻度を下げる**のではなく**頻度を上げて自動化と自信を構築する**ことで解消される。逆方向の最適化は罠
>
> 2. **原因と対策**:
>
>    1. **CI 環境と本番環境の差異**: CI では SQLite / 本番は PostgreSQL、CI ではメモリ Redis / 本番は ElastiCache、CI のタイムゾーンが UTC / 本番が JST など。**対策**: `services:` で本番と同一バージョンのコンテナを起動し、環境変数も本番と同種を再現する。Docker イメージを使い回せば差異は最小化
>    2. **テスト自体の品質不足**: カバレッジ率は高いが、アサーションが弱い / モックが過剰で実態を反映していない / Happy path のみで境界値が未検証。**対策**: ミューテーションテスト（コードを意図的に壊してテストが検出するか確認）や E2E テストで補完。カバレッジ率より「**意味のある検証があるか**」を重視
>    3. **テスト対象外の本番固有要素**: 本番固有のトラフィック量・データ量・並行アクセス・ネットワークレイテンシ・タイムゾーン跨ぎ。**対策**: ステージング環境を本番に近づけ、負荷テスト / カオスエンジニアリング（Chaos Monkey 等）でリスクを事前に表面化
>
>    補足: CI が緑でも本番で壊れる場合、「**テストの欠落**」と「**環境差異**」のどちらかが原因のことが大半。両方を切り分けて対策する
>
> 3. **修正すべき問題点**:
>
>    1. **シークレットのハードコード**: `Bearer sk_live_abc123xyz789` が YAML に直書き。**なぜ致命的か**: git 履歴から完全削除困難で、リポジトリが public でなくても**過去のコミットを `git log -p` で誰でも参照可能**。本番 API キー漏洩は確定的で、攻撃者がレートリミット内で本番 API を叩ける状態になる。修正: `${{ secrets.DEPLOY_API_KEY }}` で参照、現状のキーは即座にローテーション + 漏洩期間内のアクセスログ監査
>
>    2. **`npm install` の使用**: lockfile を尊重しない実装。**なぜ致命的か**: `package.json` で `"axios": "^1.0.0"` のような範囲指定だと、CI 実行のたびに最新パッチ版がインストールされる。**今日通った CI が来週通らない**「ビルドの時限爆弾」になり、原因特定に数時間溶ける。サプライチェーン攻撃で侵害された新バージョンを掴むリスクもある。修正: **`npm ci`** を使う(lockfile に従い決定的にインストール、なければ即エラー)
>
>    3. **テストとデプロイが同一ジョブ・直列**: 1 ジョブで実行されるためテスト失敗で `deploy` ステップに到達しないが、ジョブ分離されていない。**なぜ問題か**: 同一ジョブだと**テストの並列化** / **キャッシュ最適化** / **ジョブ単位のリトライ** ができない。CI 全体が単一の長いシーケンスになり、デプロイだけ再実行したい時にもテストから走ることになる。修正: `test` ジョブと `deploy` ジョブを分け、`needs: test` で依存させる
>
>    4. **`version=latest` の使用**: どのコミットの成果物がデプロイされたか追跡不能。**なぜ致命的か**: 本番障害が発生した時、「**今動いているコードはどのコミットか**」が分からないとロールバック先も特定できない。`latest` タグは**直前のデプロイで上書き**されるため、前バージョンの成果物すら残っていないことがある。修正: `version=${{ github.sha }}` でコミット SHA を渡し、デプロイ履歴に SHA を記録
>
>    5. **ロールバック・ヘルスチェック欠如**: デプロイ後の正常性確認と失敗時の自動戻しがない。**なぜ致命的か**: デプロイ API が 200 を返しても、起動失敗で死んでいる可能性がある。次に気づくのは**ユーザーからのクレーム**で、その間トラフィックを失う。修正: デプロイ API のレスポンスを検証 + `/health` エンドポイントを定期 poll、失敗時に前バージョンへ自動ロールバック
>
>    6. **キャッシュ未活用**: `actions/setup-node` の `cache: 'npm'` も `actions/cache` も未使用。**なぜ問題か**: 単に「実行が遅い」だけでなく、**フィードバックループ全体を蝕む**。CI が毎回 5 分余計にかかると、開発者は CI 完了を待たずに次タスクに移り、失敗通知時のコンテキストが失われる。月 200 PR で 16 時間以上の純粋な待機時間ロスになる。修正: 依存キャッシュを有効化(`hashFiles('**/package-lock.json')` でキー化)
>
>    7. **タイムアウト未設定**: ジョブが永久に走り続ける可能性。**なぜ問題か**: GitHub Actions のデフォルトタイムアウト(360 分 = 6 時間)が暗黙適用される。テスト無限ループや外部 API ハングで**6 時間 GitHub Actions の billable minutes を消費**し、料金プランによっては数千円が一瞬で消える。修正: `timeout-minutes: 15` を job に設定、step 単位でも `timeout-minutes` を設定
>
>    **思考プロセス**: AI が生成した CI/CD YAML はまず**シークレット参照**と**決定的ビルド(`npm ci`)**と**ロールバック戦略**の 3 点を最優先で確認する。AI は「動かす」を優先するため、本番運用に必要な堅牢性(タイムアウト / ロールバック / コミット SHA 追跡 / キャッシュ)が抜けがち。**「動く」と「本番で運用に耐える」の間にあるギャップを埋めるのは人間の仕事**

## 学習メモ

- CI/CDは「ツール」ではなく「プラクティス」。ツールなしでも手動で頻繁に統合・デプロイしていればCI/CDの精神は実現できる（非効率だが）
- DORA メトリクスの4指標（デプロイ頻度・リードタイム・MTTR・変更失敗率）はチームの成熟度を測る良い指標
- パイプラインの実行時間が15分を超えたら最適化を検討すべきサイン
- 「デプロイが怖い」と感じるなら、それはCI/CDの改善余地があるというシグナル
