# 不要な抽象化 — AI実装アンチパターン

> **このファイルは何か:** AIコーディングエージェントが頻発させる **「綺麗な設計」を機械的に適用して過剰になる** 系アンチパターンの横断索引。インターフェース爆発・パススルー層・早すぎるマイクロサービス化・将来拡張のためのフックなどがここに集約される。

## 一言で言うと

> **「いつか使うかも」「綺麗な設計っぽいから」で挿入される抽象化の層が、本来必要だった「変更のしやすさ」を逆に奪う。**

## 何が問題か

AI は学習データに含まれる **「教科書的なベストプラクティス」** を機械的に提案する。Clean Architecture / SOLID / マイクロサービス / CQRS — どれも文脈次第では正しい判断になるが、**「今、この規模で、この変更頻度で、本当に必要か」** の判断が抜ける。

抽象化の追加には実コストがある:
- **理解コスト** — 1機能を追うのに 5 ファイルを開く必要
- **変更コスト** — 1 つの追加で複数層を修正（ショットガン手術）
- **テスト複雑度** — モック / DI セットアップが本質ロジックを覆う
- **新人参入コスト** — 「なぜこの抽象が必要なのか」の説明から始まる

「**Rule of Three**」（3回以上完全に同じ重複が出るまで共通化しない）と「**YAGNI**」（必要になるまで作らない）の不在が、AI 生成コードに過剰抽象化を生む。

## 典型コード

### 1. インターフェース爆発（1実装1インターフェース）

```typescript
// ❌ 悪い例 — `XxxService` / `XxxServiceImpl` の機械的二重化
interface UserService {
  getUser(id: string): Promise<User>;
  createUser(input: UserInput): Promise<User>;
}

class UserServiceImpl implements UserService {
  async getUser(id: string) { /* ... */ }
  async createUser(input: UserInput) { /* ... */ }
}

// 結果: UserService と UserServiceImpl の二重メンテ
// 利点なし: 実装を交換する予定もテストでモックする予定もない
```

何が悪いか: **「いつか実装を交換するかも」のためのフックが過剰**。インターフェースは **「複数実装が必要 / モックが必要」** な場合のみ作る。

```typescript
// ✅ 良い例 — クラスを直接 export
export class UserService {
  async getUser(id: string) { /* ... */ }
  async createUser(input: UserInput) { /* ... */ }
}

// テストでモックしたいなら、その時に Mock 注入するか
// vitest の `vi.mock` で十分
```

### 2. パススルー層（中間で何もしない層）

```typescript
// ❌ 悪い例 — Controller → Service → Repository すべて1行のパススルー
class UserController {
  constructor(private service: UserService) {}
  getUser(id: string) {
    return this.service.getUser(id);
  }
}

class UserService {
  constructor(private repo: UserRepository) {}
  getUser(id: string) {
    return this.repo.findById(id);
  }
}

class UserRepository {
  findById(id: string) {
    return db.user.findUnique({ where: { id } });
  }
}
```

何が悪いか: **3層全てが1行のパススルー**で、固有のロジックがない。「変更の理由が異なる」分離になっておらず、何かを変えるたびに3ファイル修正。

**判断基準:** **「この層に固有のロジックがあるか?」** がなければ削除候補。

```typescript
// ✅ 良い例 — シンプルな Controller + ORM 直呼び
app.get('/users/:id', async (req, res) => {
  const user = await db.user.findUnique({ where: { id: req.params.id } });
  if (!user) return res.status(404).json({ error: 'Not found' });
  return res.json(user);
});
```

DB アクセスが複雑化したら、**その時点で Repository に分離** する（YAGNI）。

### 3. 早すぎるマイクロサービス化

```yaml
# ❌ 悪い例 — 数人のチームが10サービスを最初から構築
services:
  - user-service
  - auth-service
  - notification-service
  - payment-service
  - order-service
  - inventory-service
  - shipping-service
  - reporting-service
  - admin-service
  - api-gateway
```

何が悪いか:
- **ドメイン境界が固まる前**に分割 → 後で境界を引き直すコストが膨大
- 通信オーバーヘッド・分散トランザクション・サービス間認証で複雑度が爆発
- 観測 (Observability) を最初に整備しないと **何が遅いか分からない**

**正しい順序:** モノリス → モジュラーモノリス → サービス分割（痛みが出てから）。

### 4. 将来拡張のためのフック

```typescript
// ❌ 悪い例 — 「将来複数通貨対応するかも」で過剰汎用化
class Money {
  constructor(
    public amount: number,
    public currency: Currency,           // 今は JPY 1 つだけ使う
    public exchangeRate?: ExchangeRate,  // 「いつか為替対応するかも」
    public roundingMode?: RoundingMode,   // 「丸め方を選べるように」
    public formatter?: MoneyFormatter,    // 「表示形式をカスタマイズ」
  ) {}
}

// 実際の使用は new Money(1000, JPY) のみ
```

何が悪いか: 使われない引数が型と理解コストを膨らませる。**「必要になったとき」に拡張**する。今書くと、将来の本当の要件と合わない可能性が高い。

### 5. Strategy / Factory の過剰適用

```typescript
// ❌ 悪い例 — 通知方式を抽象化、しかし実装は EmailNotifier だけ
interface Notifier {
  send(message: string): Promise<void>;
}
class EmailNotifier implements Notifier { /* ... */ }
class NotifierFactory {
  static create(type: string): Notifier {
    switch (type) {
      case 'email': return new EmailNotifier();
      default: throw new Error(`Unknown: ${type}`);
    }
  }
}
```

何が悪いか: **実装が1つしかない**のに Strategy + Factory。SMS / Push が **本当に近々来る予定** なら入れてよいが、「いつか」では不要。

### 6. CQRS / イベントソーシングの早すぎる導入

```typescript
// ❌ 悪い例 — 単純な CRUD に CQRS / Event Sourcing
class CreateUserCommand { /* ... */ }
class CreateUserCommandHandler { /* ... */ }
class GetUserQuery { /* ... */ }
class GetUserQueryHandler { /* ... */ }
class UserCreatedEvent { /* ... */ }
class UserEventStore { /* ... */ }
class UserReadModelProjector { /* ... */ }
```

何が悪いか: **読み書きの非対称性が実痛になっていない**段階で CQRS。CRUD で十分なところに分離を入れると、イベント順序・整合性・リプレイ等の難しさだけが残る。

## どう直すか

### 判断基準

抽象化を入れる前に問うこと:

1. **今、複数の実装が必要か？** （Yes でなければ抽象化しない）
2. **テストで本当にモックしたいか？** （多くは Fake / 実物で十分）
3. **3 回以上同じ重複が出ているか？** （Rule of Three）
4. **この層に固有のロジックがあるか？** （パススルーなら削除）
5. **境界が固まっているか？** （マイクロサービス化前に必須）

### 直し方の比較

| 悪いパターン | 直し方 |
|---|---|
| 1実装1インターフェース | 削除、クラスを直接 export |
| パススルーの中間層 | 削除、上下を直接接続 |
| 早すぎるマイクロサービス化 | モノリス / モジュラーモノリスに戻す |
| 将来用の引数 / フィールド | 削除、必要時に追加 |
| 単一実装の Strategy / Factory | 削除、直接呼ぶ |
| 早すぎる CQRS | 統合 CRUD に戻す |

## レビュー観点

1. **このインターフェースは複数実装があるか？** — 1つなら削除候補
2. **この層は固有のロジックを持つか？** — パススルーなら削除
3. **使われていない引数 / フィールドがあるか？** — YAGNI
4. **同じ抽象化を別の場所で 3 回以上見たか？** — 1〜2回なら早すぎる共通化
5. **マイクロサービス分割の根拠は「組織」「スケール」「変更頻度」のどれか？** — 「綺麗だから」は不採用

## 「これだけ AI に伝える」追プロンプト

```
以下のコードから不要な抽象化を削除してください。

削除基準:
- 1実装しか存在しない interface (XxxService と XxxServiceImpl 等)
- 中間でパススルーするだけの層 (固有ロジックなし)
- 将来使うかもしれないが現在使われていない引数 / フィールド / メソッド
- 単一実装の Strategy / Factory パターン
- 「綺麗だから」で導入された CQRS / イベントソーシング

判断基準 (Rule of Three):
- 同じ重複が 3 回以上出るまで共通化しない
- 抽象化の前に「今、複数実装が必要か?」「テストでモックしたいか?」を問う

維持する:
- 既に 3 つ以上の実装がある抽象化
- 公開 API として外部に提供する境界
- 複雑なドメインロジックの分離 (このコードに該当する場合)
```
