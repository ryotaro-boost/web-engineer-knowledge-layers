# 既存ユーティリティの再発明 — AI実装アンチパターン

> **このファイルは何か:** AIコーディングエージェントが頻発させる **「プロジェクト内の既存実装を見ずに自前で書く」** 系アンチパターンの横断索引。標準ライブラリ・社内ユーティリティ・既存ミドルウェアの再発明がここに集約される。

## 一言で言うと

> **AIは「新しく書く」ことが得意で「既に何があるか」を知らない**。結果、プロジェクト内の既存実装と機能が重複し、規約逸脱・バグの分散・保守コストの増大を招く。

## 何が問題か

AI に「機能 X を実装して」と頼むと、**既存コードを横断的に検索せず**に新規実装を書く。たとえコンテキストとしてプロジェクトを渡していても、関連する既存ユーティリティを見落とす確率が高い。結果:

- **規約からの逸脱** — エラーハンドリング方針 / ログ形式 / 命名が既存と違う
- **バグの分散** — 既存実装で直した不具合が新実装に残る
- **保守コストの倍増** — 同じ機能が複数箇所に
- **テスト漏れ** — 既存のテストヘルパーを使わず独自実装し、エッジケースが抜ける
- **セキュリティリスク** — 既存の検証済み実装を使わず、自前実装に脆弱性が混入

## 典型コード

### 1. 標準ライブラリの再発明

```typescript
// ❌ 悪い例 — Lodash や標準 Array.from を使わずに自前実装
function unique(arr: number[]): number[] {
  const result: number[] = [];
  for (const item of arr) {
    if (!result.includes(item)) result.push(item);
  }
  return result;
}
// 計算量 O(n²)、しかも既存にもっと良い実装がある

// ✅ 良い例
function unique<T>(arr: T[]): T[] {
  return Array.from(new Set(arr));
}
```

```python
# ❌ 悪い例 — itertools を知らずに自前実装
def chunks(lst, n):
    result = []
    for i in range(0, len(lst), n):
        result.append(lst[i:i+n])
    return result

# ✅ 良い例
from itertools import batched
list(batched(lst, n))  # Python 3.12+
```

### 2. 社内ユーティリティの再発明

```typescript
// プロジェクトに既に `src/utils/http.ts` の apiClient があるのに、
// AI が新規ハンドラで素のfetchを直接書く

// ❌ 悪い例 — 認証ヘッダ・エラーハンドリング・リトライを毎回再実装
const response = await fetch(`${API_BASE}/users/${id}`, {
  headers: {
    'Authorization': `Bearer ${token}`,
    'Content-Type': 'application/json',
  },
});
if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}
return response.json();

// ✅ 良い例 — 既存ユーティリティを使う
import { apiClient } from '@/utils/http';
return apiClient.get(`/users/${id}`);
```

### 3. 既存ミドルウェアの再発明

```typescript
// プロジェクトに `authMiddleware` があるのに、AI が各ハンドラで認証を直書き

// ❌ 悪い例
app.get('/users/:id', async (req, res) => {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'No token' });
  const user = await verifyJWT(token);
  if (!user) return res.status(401).json({ error: 'Invalid token' });
  // ... 本処理
});

// ✅ 良い例 — 既存ミドルウェアを使う
app.get('/users/:id', authMiddleware, async (req, res) => {
  // req.user が既にセットされている
});
```

### 4. ロギング機構の再発明

```typescript
// プロジェクトに structured logger (winston / pino / structlog) があるのに、AI は console.log

// ❌ 悪い例
console.log('User created:', userId);
console.error('DB failed:', err);

// ✅ 良い例 — 既存ロガーを使う
logger.info({ event: 'user_created', userId });
logger.error({ event: 'db_error', err }, 'Database operation failed');
```

### 5. 既存の Fake / Test Helper の再発明

```typescript
// テストフォルダに `tests/fixtures/userFactory.ts` があるのに、AI が毎回手動でユーザを作る

// ❌ 悪い例
const user = {
  id: '1',
  email: 'test@example.com',
  passwordHash: 'fakehash',
  createdAt: new Date(),
  updatedAt: new Date(),
  // ... 全フィールド埋める
};

// ✅ 良い例
import { userFactory } from '@tests/fixtures';
const user = userFactory.build({ email: 'test@example.com' });  // 他はデフォルト
```

### 6. 既存のサーキットブレーカー / リトライ実装の再発明

```typescript
// プロジェクトに `withCircuitBreaker` / `withRetry` があるのに、AI が自前実装

// ❌ 悪い例
let attempt = 0;
while (attempt < 3) {
  try {
    return await externalApi.call();
  } catch (err) {
    attempt++;
    await sleep(1000 * attempt);
  }
}
throw new Error('Failed after 3 attempts');
// ジッターなし、サーキットブレーカーなし、ログなし

// ✅ 良い例
return await withRetry(() => externalApi.call(), { maxAttempts: 3 });
```

## どう直すか

### 原則

1. **コード生成前に「既存にあるか」を必ず探す** — `grep` で類似機能を探す習慣
2. **AI に「既存ユーティリティを使え」と明示する** — プロンプトで `src/utils/` `src/lib/` を参照させる
3. **規約 (CLAUDE.md / CONTRIBUTING.md) で既存パターンを記述** — AI に読ませる
4. **PR レビューで「既存にあったら指摘」を徹底**

### 探し方の手順

| 機能 | 探す場所 |
|---|---|
| 文字列・配列操作 | 標準ライブラリ → Lodash/itertools などプロジェクト依存 → `src/utils/` |
| HTTP リクエスト | `src/api/` `src/lib/http.ts` |
| 認証・認可 | `src/middleware/` `src/lib/auth.ts` |
| バリデーション | `src/schemas/` `src/validators/` |
| ロギング | `src/lib/logger.ts` |
| エラー型 | `src/errors/` |
| テストヘルパー | `tests/fixtures/` `tests/factories/` |
| DB アクセス | `src/db/` `src/repositories/` |

## レビュー観点

1. **この機能は標準ライブラリにないか？** — 多くは `Array.from(new Set())` 等で済む
2. **プロジェクト内の `utils/` `lib/` にないか？** — `grep` で類似機能を探す
3. **既存の規約（エラー型・ログ形式・命名）に沿っているか？**
4. **テストで既存の Factory / Helper を使っているか？**

## 「これだけ AI に伝える」追プロンプト

```
以下の機能を実装する前に、必ず以下を確認してください:

1. 標準ライブラリに同等の機能がないか
2. プロジェクト内の `src/utils/` `src/lib/` `src/middleware/` に既存実装がないか
3. 既存の規約 (CLAUDE.md / CONTRIBUTING.md / 周辺コード) に沿った形式か

実装前にプロジェクトを以下のキーワードで検索してください:
- <機能のキーワード> 例: "retry", "circuit", "logger", "fetch wrapper"
- <類似機能の関数名> 例: "apiClient", "withAuth", "userFactory"

既存実装がある場合はそれを使い、ない場合のみ新規実装してください。
新規実装する場合は、周辺コードのスタイル (エラーハンドリング・ログ形式・命名) に合わせてください。
```
