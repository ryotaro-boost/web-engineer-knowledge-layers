# 過剰なフォールバック — AI実装アンチパターン

> **このファイルは何か:** AIコーディングエージェントが頻発させる **「起こりえないケースに備える」** 系アンチパターンの横断索引。レイヤー別索引に散らばる該当例を、**根が同じ癖** として一箇所に集める。

## 一言で言うと

> **「念のため」「とりあえず」で挿入される try/catch・デフォルト値・retry が、本来検出すべきバグを隠蔽し、データ不整合の温床になる。**

## 何が問題か

AI は「**安全側に倒す**」ことを学習データから過剰に学んでいる。結果、人間のエンジニアなら書かないレベルでフォールバックを大量挿入する:

- 起こりえないケースへの try/catch
- 「念のため」の `?? null` `|| {}`
- 失敗を隠蔽する `catch { return [] }` `catch { return null }`
- 真因を究明しない `retry: 3`
- 内部関数の引数 NULL チェック（型システムが既に保証）

これらは **「動かなくなる」**よりも危険な **「動いたつもりで壊れている」** 状態を作る。

## 典型コード — 過剰なフォールバックの見本市

### 1. 失敗を隠蔽する catch (最頻出)

```typescript
// ❌ 悪い例 — エラーを握りつぶし、空配列を返す
async function getUserPosts(userId: string) {
  try {
    return await db.posts.findMany({ where: { userId } });
  } catch (err) {
    return [];  // 失敗もデータ無しも区別がつかない
  }
}
```

何が起きるか: **DB接続失敗 = 投稿0件** として表示される。ユーザは「投稿を消された?」と思う。監視は何も鳴らない。

```typescript
// ✅ 良い例 — エラーは伝播、フォールバックは要件で明示
async function getUserPosts(userId: string) {
  return await db.posts.findMany({ where: { userId } });
}
```

### 2. 「念のため」のデフォルト値

```typescript
// ❌ 悪い例 — 起こりえない null を防御
function calculateTotal(order: Order): number {
  const items = order.items ?? [];        // Order型が items: Item[] を保証している
  const tax = order.tax ?? 0;             // 同上
  return items.reduce((sum, i) => sum + i.price * (1 + tax), 0);
}
```

何が悪いか: **TypeScript の型保証を信じていない**。スキーマで NOT NULL 保証されているのにコードで再防御することで、本当のバグ（型と実体のズレ）が起きた時に気づけなくなる。

### 3. 真因を究明しない retry

```yaml
# ❌ 悪い例 — フレイキーテストを retry で誤魔化す
test:
  retry: 3
  command: npm test
```

何が起きるか: **テストが通っているように見えるが、本当は壊れている**。順序依存・時刻依存・非同期の `await` 漏れなど真因が放置され、本番で別の形で噴出する。

### 4. ネストする try/catch

```python
# ❌ 悪い例 — 各層に try/catch、全部潰す
def process_order(order_id):
    try:
        order = get_order(order_id)
        try:
            charge = charge_payment(order)
            try:
                send_email(order)
            except Exception:
                pass  # メール失敗は無視
        except Exception:
            return None  # 決済失敗は None
    except Exception:
        return None  # 取得失敗も None
```

何が起きるか: **どの段階で失敗したか分からない**。「決済失敗で None」と「取得失敗で None」が同じ。リトライ判断もできない。

### 5. 内部関数のバリデーション

```typescript
// ❌ 悪い例 — 内部関数で「念のため」型チェック
function calculateDiscount(price: number, rate: number): number {
  if (typeof price !== 'number') return 0;     // TS が保証
  if (typeof rate !== 'number') return 0;       // TS が保証
  if (price < 0) return 0;                      // 起こりえない (要件次第)
  return price * rate;
}
```

外部入力を受ける関数（API ハンドラ）はバリデーション必須。**内部関数は型システム / スキーマを信頼**する。

## どう直すか

### 原則

1. **エラーは握りつぶさず、伝播させる** — 呼び出し元が文脈に応じて判断する
2. **フォールバックは「要件」として明示** — 「DB 失敗時は空配列を返す」が要件なら、その意図がコードから読めるように
3. **retry は真因究明後の最終手段** — フレイキーテストは真因を直す
4. **内部関数は型/スキーマを信頼** — 多重チェックは可読性とのトレードオフで負けがち
5. **境界 (外部入力 / 外部 API) のみバリデーション**

### 直し方の比較

| 悪いパターン | 直し方 |
|---|---|
| `catch { return [] }` | エラーを伝播。空配列が要件なら型で `Result<Item[], DbError>` などで明示 |
| `?? null` `|| {}` | 型で NOT NULL 保証されているなら削除 |
| 全関数に try-catch | フレームワークの集約エラーハンドラに任せる |
| `retry: 3` | フレイキーの真因を究明、retry はネットワーク要因の境界呼び出しのみ |
| 内部関数の null チェック | 削除。境界での1回のバリデーションに集約 |

## レビュー観点（コードを見るときの問い）

1. **この catch は何を守っているのか？** — 答えられないなら不要
2. **フォールバック値で「成功」と「失敗」が区別できるか？** — `[]` が「データなし」と「DB失敗」両方を意味するのは危険
3. **retry の真因は突き止めたか？** — 「とりあえず」が言葉に出るなら止める
4. **内部関数のチェックは型システムが既に保証していないか？** — 多くは削除可
5. **エラーが起きたとき監視は気づくか？** — 握りつぶすと監視も気づけない

## 「これだけ AI に伝える」追プロンプト

AI 生成コードに過剰なフォールバックが混入していたら、以下のプロンプトで修正させる:

```
以下のコードから過剰なフォールバックを削除してください。

削除基準:
- 型システム / スキーマ / 上流バリデーションで既に保証されている条件への重複チェック
- エラーを握りつぶす catch (`return null` `return []` `return {}` 含む)
- 「念のため」の ?? / || デフォルト値
- 真因究明なしの retry / sleep

削除しない:
- 外部入力（HTTPリクエスト・ファイル・環境変数）の境界バリデーション
- ネットワーク呼び出しの retry（指数バックオフ + ジッターで明示的に設計）
- 要件で明示されたフォールバック（コメントで意図を残す）

エラーは原則として呼び出し元へ伝播させ、最終的な処理はフレームワーク標準のエラーハンドラに集約してください。
```
