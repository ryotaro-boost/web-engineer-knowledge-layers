# Layer 0: CS基礎 — AI実装アンチパターン集

> Layer 0（[[データ構造とアルゴリズム]] / [[計算量-BigO]] / [[文字コード-UTF8]] / [[並行性の基本概念]]）の改修で集約された、AIコーディングエージェントが頻発させるアンチパターンの索引。

## このレイヤーで頻出する「AIの癖」

CS基礎層のコードは Layer 1（OS）や Layer 2（ネットワーク）と違って I/O・外部リソース・分散の概念が薄いため、AI のアンチパターンは **「過剰な最適化・抽象化・防御」に集中する**。共通する根:

- **「起こりえない状態への過剰防御」** — 内部関数への null チェック連鎖、入力が型システムで保証されているのに「念のため」の if、API レスポンスにも DB 接続失敗にも全部フォールバックを書く
- **「小さい n / シンプルな処理への過剰最適化」** — 10 件の配列にバイナリサーチ、20 件の選択肢に Map 化、明らかな処理に `// O(n)` コメント
- **「標準機能の薄いラッパー化」** — `arr.length === 0` を `isEmpty(arr)` でラップ、`Map` を `UserCollection` クラスでラップ、`map.get(k) ?? default` を `safeGet(map, k, default)` でラップ
- **「文字とバイトの混同」** — `maxlength=100` を `Buffer.byteLength()` で判定、UTF-8 推測デコード（fallback chain）、サロゲートペア無視で絵文字が壊れる
- **「並行性での同期プリミティブ誤用」** — 全変数にミューテックス、`sleep()` でタイミング合わせ、`await` 逐次化で並行性の利点を消す

これらは多くがレイヤー横断のパターン（**過剰なフォールバック / 防御的すぎるエラーハンドリング / 不要な抽象化 / 既存ユーティリティの再発明**）に紐付く。Layer 0 の特徴は **「外的要因がほぼないのにアンチパターンが発生する」** こと — つまり AI が内部で勝手に複雑性を増やしている兆候。

## トピック別アンチパターン索引

### [[データ構造とアルゴリズム]]

| アンチパターン | レビュー観点 |
|---|---|
| コレクションの不要なラッパークラス（`UserCollection` 等で `Map`/`Array` を包む） | 標準コレクション API をそのまま使う。ドメイン固有ロジックがない限り抽象化しない |
| 防御的すぎる null チェックの連鎖（内部関数で `if (!arr) return [];` を多段） | システム境界のみバリデーション。内部は型システムを信頼 |
| 不要なユーティリティ関数の量産（`isEmpty`, `safeGet` 等の薄いラッパー） | 標準の演算子・メソッドを直接使う。`arr.length === 0`, `map.get(k) ?? default` |
| 小さなデータセットへの過剰なアルゴリズム適用（10件にバイナリサーチ） | n の現実的な上限を確認。n ≤ 数十件なら `find()` / `includes()` で十分 |

### [[計算量-BigO]]

| アンチパターン | レビュー観点 |
|---|---|
| 早すぎるキャッシュ導入（数十件のデータ取得に Redis やメモ化） | プロファイルで実際にボトルネックを確認してから。「将来大きくなるかも」は理由にならない |
| 小さなデータセットへの過剰な最適化（管理画面 20 件に `Map` 化） | n の現実的な上限を見積もり、O(n²) でも問題ないなら素直に書く |
| フォールバックの多重実装（API 遅延・キャッシュミス・DB 失敗の全シナリオに事前対応） | 実際に起きている / 確率の高い問題だけに対処。「もし〜なら」の連鎖で防御を積み重ねない |
| 計算量コメントの過剰付与（全関数に `// O(n)` `// O(1)`） | 非自明な計算量（O(n²) が隠れている等）にだけ注記 |

### [[文字コード-UTF8]]

| アンチパターン | レビュー観点 |
|---|---|
| バイト長と文字数を混同したバリデーション（`maxlength=100` をバイト数で） | 要件に応じてコードポイント数 / 書記素クラスタ数で数える。`Intl.Segmenter` を使う |
| エンコーディング変換の過剰なフォールバック（UTF-8 → Shift_JIS → EUC-JP の推測デコード） | 仕様でエンコーディングを固定する。推測しない設計にする |
| サロゲートペアを考慮しない正規表現（絵文字に `.` がマッチしない） | ES2015 の `u` フラグ付き正規表現を使う |
| BOM の無条件付与 / 除去（用途を区別せず一律操作） | 用途に応じて BOM の有無を制御。CSV を Excel に渡す時のみ付ける |

### [[並行性の基本概念]]

| アンチパターン | レビュー観点 |
|---|---|
| 全てにミューテックスを付ける | 本当に共有される状態だけをロック。不要なロックはデッドロックリスクを増やす |
| `sleep()` で競合を「回避」 | 適切な同期プリミティブ（セマフォ、条件変数、Promise）を使う |
| `async/await` の過剰な直列化（独立処理を逐次 `await`） | 独立した処理は `Promise.all()` / `asyncio.gather()` で並行実行 |
| エラーハンドリングなしの並行処理（1つの失敗が他を巻き込む） | 個別のエラーハンドリングと適切なキャンセル処理 |
| スレッドプールサイズのハードコード | CPU コア数ベースの動的設定、または環境変数で設定可能に |

## レイヤー横断の共通テーマ

Layer 0 のアンチパターンは、より上位の **「パターン別」** カテゴリに属するものが多い:

- **過剰なフォールバック** — エンコーディング推測 fallback chain、API/DB/キャッシュ全てへの事前フォールバック、`?? default` の連鎖
- **防御的すぎるエラーハンドリング** — 内部関数への null/undefined チェック、型が保証している不変条件への `if`、起こりえない状態への防御
- **不要な抽象化** — `UserCollection` のような1箇所しか使わないラッパー、薄いユーティリティ関数の量産
- **既存ユーティリティの再発明** — `isEmpty(arr)`、`safeGet(map, k, default)` のような言語標準で1行で書ける処理を関数化
- **小さな n への過剰最適化** — プロファイル結果なしに「念のため」最適化を入れる。コードの複雑性が増える割に効果がない

## このレイヤーを読むときの観点

Layer 0 は他レイヤーと違って **AI が「自分で複雑性を作り出す」傾向が顕著に出る層**。「外部要因に対処している」風のコードでも、よく見ると「型・標準ライブラリで保証されている不変条件への防御」になっていることが多い。レビュー時は以下を問う:

1. **この防御コード、内部関数で本当に必要か** — 型システムが既に保証していないか
2. **この最適化、n の上限を確認したか** — 小さな n では素直な書き方の方が速い場合もある（CPU キャッシュ、分岐予測等）
3. **このラッパー、標準機能で1行で書けないか** — チーム内統一以外の動機があるか
4. **この並行処理、本当に共有状態か** — 共有を減らす設計（メッセージパッシング、不変オブジェクト）にできないか
