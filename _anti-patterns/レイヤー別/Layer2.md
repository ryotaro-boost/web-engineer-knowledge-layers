# Layer 2: ネットワーク — AI実装アンチパターン集

> Layer 2（[[TCP-IP]] / [[DNS]] / [[HTTP-HTTPS]] / [[TLS-SSL]] / [[WebSocket]]）の改修で集約された、AIコーディングエージェントが頻発させるアンチパターンの索引。

## このレイヤーで頻出する「AIの癖」

ネットワーク層のコードは「**ローカルでは動くが、本番のレイテンシ・パケットロス・スケール・敵対的な入力に晒されると壊れる**」コードを AI が量産しやすい。Layer 2 のアンチパターンには次の共通する根がある:

- **「タイムアウト・リトライ・上限を設定しない」** — `fetch()` 一行、`requests.get()` 一行で済ませる。本番でハングしてカスケード障害を引き起こす
- **「コネクションを使い回さない」** — リクエストごとに新規 HTTPClient を作る。3ウェイハンドシェイク + TLS ハンドシェイクが毎回発生してレイテンシ激増、`TIME_WAIT` 蓄積でポート枯渇
- **「セキュリティを `*` または `false` で済ます」** — CORS の `Allow-Origin: *`、TLS の `verify=False`、Origin 検証なし WebSocket。「動かないから」で AI が安易に追加する
- **「メソッド・ステータスコードのセマンティクスを無視」** — 全部 POST、エラーも 200、削除を GET。HTTP インフラの恩恵をすべて捨てる
- **「キャッシュ・TTL・再接続・自動更新を考慮しない」** — `Cache-Control` 未設定、TTL=0、再接続なし、証明書手動更新。本番運用で必ず破綻する

これらは多くがレイヤー横断のパターン（**過剰なフォールバック / 防御的すぎるエラーハンドリング / 既存機能の再発明 / 起こりえないケースへの対処**）に紐付く。

## トピック別アンチパターン索引

### [[TCP-IP]]

| アンチパターン | レビュー観点 |
|---|---|
| ソケット通信を生で実装 | 言語標準のHTTPクライアントを使う |
| タイムアウトなしのネットワーク呼び出し | 接続・読み取り・全体のタイムアウトを必ず設定 |
| リトライを即座に無限回 | 指数バックオフ + ジッター + 最大回数。冪等な操作のみ |
| リクエストごとに HTTPClient を新規生成 | 上位スコープで生成し、コネクションプール / Keep-Alive で再利用 |
| エラー時にコネクションを閉じない | `try-finally` / `context manager` / `defer` で確実にクローズ |
| 全エラーを `catch` して握りつぶす | リトライしないエラーは上位に再 throw |

### [[DNS]]

| アンチパターン | レビュー観点 |
|---|---|
| アプリ内で DNS 結果をハードコード | ドメイン名を使い、DNS 解決を OS / HTTP クライアントに任せる |
| DNS ルックアップ結果を無期限キャッシュ | TTL を尊重。Java の `networkaddress.cache.ttl=-1` を上書き |
| CNAME チェーンを深くネスト | 1段、多くても2段。`dig +trace` で確認 |
| ゾーン頂点（apex）に CNAME を設定 | alias レコード（Route 53）/ ANAME（Cloudflare）を使う |
| TTL=0 で「キャッシュさせない」 | 短くしたい場合は 30-60 秒。フェイルオーバーは alias + ヘルスチェック |
| DNS 設定を Console / GUI で直接操作 | Terraform / IaC で管理し PR レビュー |
| DNSSEC の鍵ローテーション忘れ | 自動ローテーション + 期限監視 |

### [[HTTP-HTTPS]]

| アンチパターン | レビュー観点 |
|---|---|
| すべてのエンドポイントを POST | リソース取得=GET、作成=POST、置換=PUT、部分更新=PATCH、削除=DELETE |
| エラーを 200 で返しボディに `{"error": true}` | 4xx/5xx を使い分け、ボディは Problem Details (RFC 7807) |
| `Cache-Control` 未設定でブラウザ任せ | 全レスポンスに明示。静的=long+immutable、API=private+短い max-age、機密=no-store |
| `no-cache` で「キャッシュしない」のつもり | 機密データは `no-store`。`no-cache` は「保存して使う前に再検証」 |
| CORS を `Allow-Origin: *` で雑に解決 | オリジンを列挙。credentials を使う場合は `*` 不可 |
| 301 と 302 を混同 | 一時的=302/307/308、恒久的=301（ブラウザがキャッシュする） |
| HTTPS を開発環境で使わない | mkcert でローカル CA。本番との挙動差を防ぐ |
| User-Agent だけでボット判定 | TLS フィンガープリント・ヘッダ順序・行動分析を組み合わせる |

### [[TLS-SSL]]

| アンチパターン | レビュー観点 |
|---|---|
| TLS 証明書の検証を無効化（`verify=False` 等） | 正しい CA 証明書を設定。社内 CA は信頼ストアに追加 |
| 古い TLS バージョンやレガシー暗号スイートを許可 | TLS 1.2 以上のみ、AEAD 暗号スイートのみ |
| 秘密鍵をソース / Docker イメージに含める | 環境変数 / シークレットマネージャー / ボリュームマウント |
| HTTP→HTTPS リダイレクトだけで HSTS なし | HSTS + preload リスト登録 |
| 0-RTT で POST リクエストを受け付ける | 0-RTT は冪等な操作（GET）のみ |
| 手動で証明書を更新 | certbot / ACM / cert-manager で自動更新 + 期限監視 |
| 自己署名証明書を本番で使い回す | 開発=mkcert、本番=Let's Encrypt / ACM |
| `Allow Insecure` 環境変数で本番でも検証バイパス可能に | コード上から完全除去。CA 差し替えで対応 |

### [[WebSocket]]

| アンチパターン | レビュー観点 |
|---|---|
| 再接続ロジックなし | 指数バックオフ + ジッター + 上限付きの再接続を最初から |
| 再接続を即座に無限リトライ | バックオフ + 上限。リトライストーム防止 |
| Origin ヘッダの検証なし | 許可リストで検証。CSWSH 防止 |
| 全メッセージを全クライアントにブロードキャスト | ルーム / チャネル単位 + 権限チェック |
| WebSocket だけで全通信 | リアルタイム性が必要な箇所のみ。他は HTTP API |
| メッセージパースのエラー処理なし | `try/catch` で囲み、不正メッセージにはエラーフレーム |
| Ping/Pong ヘルスチェックなし | サーバー・クライアント両方で定期 ping + 応答監視 |
| ステートをサーバーローカルメモリに保持してスケールアウト | Redis Pub/Sub 等で複数サーバー間に伝播。状態は外部ストア |

## レイヤー横断の共通テーマ

Layer 2 のアンチパターンは、より上位の **「パターン別」** カテゴリに属するものが多い:

- **過剰なフォールバック** — `verify=False` で証明書エラー隠蔽、`*` で CORS 許可、`try/catch` でネットワークエラー握りつぶし
- **防御的すぎるエラーハンドリング** — エラーレスポンスを 200 で返してフラグ判定、内部で全例外を catch
- **既存機能の再発明** — ソケットを生で書く、HTTPクライアントを自前実装、再接続ロジックを毎回書き直す
- **起こりえないケースへの対処** — 内部 API の証明書を `verify=False` で「念のため」、ローカルテスト用の Allow-Origin を本番にも残す
- **リソース管理の責任放棄** — タイムアウトなし、コネクション使い捨て、再接続なし、TIME_WAIT 蓄積、Ping/Pong なし
