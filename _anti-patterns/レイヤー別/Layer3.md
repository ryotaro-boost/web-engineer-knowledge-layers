# Layer 3: データ永続化 — AI実装アンチパターン集

> Layer 3（[[RDB]] / [[Resources/Study/Layer3-データ永続化/インデックス|インデックス]] / [[NoSQL]] / [[キャッシュ戦略]] / [[マイグレーション]]）の改修で集約された、AIコーディングエージェントが頻発させるアンチパターンの索引。

## このレイヤーで頻出する「AIの癖」

データ永続化層のコードは「**ローカルの空テーブルでは動くが、本番の数百万行・並行アクセス・障害シナリオに晒されると壊れる**」コードを AI が量産しやすい。Layer 3 のアンチパターンには次の共通する根がある:

- **「制約を信頼しない防御コード」** — NOT NULL カラムへの `COALESCE` / `IFNULL`、`SELECT *`、過剰な NULL チェック。スキーマで保証されている不変条件をアプリ側でも再チェックして冗長になる
- **「念のため全部カバー」設計** — 全カラムにインデックス、全テーブルにソフトデリート、全 JOIN カラムにインデックス、全エンドポイントにキャッシュ。「使うかもしれない」で過剰設計
- **「本番規模を想定しない一括処理」** — 数百万行の一括 UPDATE、`CONCURRENTLY` なしの `CREATE INDEX`、ALTER TABLE をトランザクションで包む、Scan / 全件 find の混入。開発DBでは一瞬でも本番では止まる
- **「アクセスパターン抜きの NoSQL 設計」** — RDB の正規化思想をそのまま MongoDB / DynamoDB に持ち込む。$lookup や Scan の多用、ホットパーティション
- **「キャッシュ無効化と変動軸の漏れ」** — キーにロケール/通貨/ユーザーが含まれない、TTL 固定値、無効化トリガー設計なし、Redis 障害時にアプリ全体ダウン
- **「マイグレーションのデータ損失リスク無頓着」** — カラムリネームを DROP+ADD で生成、down マイグレーションを過信、Expand-Contract 知らず

これらは多くがレイヤー横断のパターン（**過剰なフォールバック / 防御的すぎるエラーハンドリング / 既存機能の再発明 / 起こりえないケースへの対処 / 本番規模軽視**）に紐付く。

## トピック別アンチパターン索引

### [[RDB]]

| アンチパターン | レビュー観点 |
|---|---|
| 全カラムにインデックスを付与 | 実際のクエリパターンに基づき複合インデックスで集約 |
| 過剰な NULL チェック・COALESCE | スキーマ制約を信頼。NULL 許容カラムだけに適用 |
| 全テーブルにソフトデリート | 法的・ビジネス要件で必要なテーブルだけに適用 |
| `SELECT *` | 必要カラムを明示。Index Only Scan を活かす |
| 分離レベルを無条件で SERIALIZABLE | デフォルトで十分か検討、必要箇所だけ引き上げ |
| 大量 INSERT / IN 句のパラメータ数を意識しない | カラム数 × 行数を事前計算、バッチ分割または COPY/LOAD DATA |
| トランザクション内にユーザー入力待ち | 取得 → 処理 → 短いトランザクションで更新の3段に分離 |
| ループ内で個別 SELECT (N+1) | JOIN または `IN (...)` でまとめて取得、ORM では eager loading |
| 外部キー制約を省略 | DB 層でも整合性保証。`ON DELETE` は RESTRICT 既定 |
| ENUM 型 | VARCHAR + CHECK 制約で代替（マイグレーションが楽） |
| ランダム UUID v4 を主キーに使用 | UUID v7 / ULID で時系列ソート可能、B-Tree 局所性を保つ |

### [[Resources/Study/Layer3-データ永続化/インデックス|インデックス]]

| アンチパターン | レビュー観点 |
|---|---|
| 「念のため」インデックス | クエリと結びつけて理由明示、`pg_stat_user_indexes` で監視 |
| 複合インデックスのカラム順を「使用順」で決める | 等値→範囲→ORDER BY の順 |
| 関数を適用したカラムへの検索 | 式インデックス、またはアプリ側で正規化保存 |
| `CREATE INDEX` を本番テーブルに `CONCURRENTLY` なしで実行 | PostgreSQL は `CONCURRENTLY`、MySQL は `ALGORITHM=INPLACE, LOCK=NONE` |
| 全 JOIN カラムにインデックス | 小テーブル同士の JOIN ではオーバーヘッド優位 |
| `SELECT *` でカバリングインデックスを無効化 | 必要カラムだけ指定、Index Only Scan を活かす |
| 主キー / UNIQUE と重複したインデックス | 既存インデックスを `pg_indexes` で確認 |
| `(a, b)` がある状態で `(a)` を別途作成 | `(a, b)` が `(a)` の検索もカバーするため不要 |

### [[NoSQL]]

| アンチパターン | レビュー観点 |
|---|---|
| MongoDB / DynamoDB のスキーマ未定義 | Mongoose Schema / TypeScript 型 / DynamoDB AttributeDefinitions を必ず使う |
| 全データを Redis に保存 | Redis はキャッシュ・揮発カウンタ用途に限定、マスターデータは RDB |
| DynamoDB で Scan + FilterExpression | GSI/LSI を設計、Query で完結させる |
| ドキュメント DB で N+1 (個別 fetch ループ) | 埋め込み、`$lookup`、`BatchGetItem` でまとめて取得 |
| RDB 設計をそのまま NoSQL に持ち込む | アクセスパターン駆動で非正規化（埋め込み） |
| ホットパーティションを生む PK 設計 | 高カーディナリティのキー、必要ならランダムサフィックス |
| 無制限の配列成長 | Bucket Pattern で一定サイズごとに分割 |
| Redis で `KEYS *` / `FLUSHDB` を本番実行 | `SCAN` を使う、本番への直接接続を制限 |
| MongoDB の `find()` 全件取得 → アプリでフィルタ | Aggregation Pipeline で `$match + $group` をDB側で実行 |
| 結果整合性を考慮しない設計 | Read-after-Write 要件を明確化、必要なら強い整合性オプション |

### [[キャッシュ戦略]]

| アンチパターン | レビュー観点 |
|---|---|
| 全エンドポイントにキャッシュ追加 | アクセスパターンを分析、ヒット率の高い箇所に限定 |
| TTL を固定値でハードコード | 環境変数化、データ種別ごとに別 TTL |
| キャッシュキーに変動軸（ユーザー / ロケール / 通貨）が漏れる | 全変動軸を含める。漏れは別ユーザーへのデータ事故 |
| キャッシュミス時にエラーログ・リトライ | ミスは正常動作、通常フローで処理 |
| TTL ジッターなし | `TTL = base + random(±jitter)` で同時期限切れを分散 |
| Redis 接続を毎リクエスト作成 | コネクションプールを再利用 |
| 巨大オブジェクトをそのままキャッシュ | 必要フィールドだけ抽出してシリアライズ |
| キャッシュ依存の可用性 | Cache-Aside + DB 直接フォールバックで耐障害性 |
| 更新時のキャッシュ無効化漏れ | 更新パスで対応キーを必ず削除、無効化対象をマップ化 |
| エラー結果をキャッシュ | DB エラー時は保存しない、`null` キャッシュは短い TTL |
| `no-cache` で「キャッシュさせない」のつもり | 機密データは `no-store`。`no-cache` は再検証 |

### [[マイグレーション]]

| アンチパターン | レビュー観点 |
|---|---|
| カラム名変更を DROP + ADD で生成 | `RENAME COLUMN` か Expand-Contract で段階的に |
| down マイグレーションの過信 | 本番では Forward Fix を採用、down は開発時のみ |
| 全テーブル一括 UPDATE | バッチ処理（1000行 + スリープ + 進捗ログ） |
| マイグレーション内でアプリケーションコードを呼び出す | 生 SQL かマイグレーション専用クエリ |
| 大規模テーブルへのインデックス追加を無計画に実行 | PostgreSQL は `CONCURRENTLY`、MySQL は `ALGORITHM=INPLACE` |
| `ALTER TABLE` で複数操作を1文に詰め込む | 1マイグレーション = 1論理変更 |
| `NOT NULL` カラムをデフォルト値なしで追加 | NULL 許容で追加 → バックフィル → NOT NULL の3段階 |
| ENUM 型の値追加・削除 | VARCHAR + CHECK 制約で代替 |
| 適用済みマイグレーションファイルの編集 | 必ず新規ファイルで修正（イミュータブル原則） |
| 巨大トランザクションで包む | スキーマ変更とデータ変更を分離、トランザクション最小化 |
| 本番 DB で手動 SQL 実行 | すべての変更をマイグレーションファイル経由 |

## レイヤー横断の共通テーマ

Layer 3 のアンチパターンは、より上位の **「パターン別」** カテゴリに属するものが多い:

- **過剰なフォールバック** — NOT NULL カラムへの `COALESCE`、Redis 障害時に「念のため」キャッシュミス扱いにせずエラー throw、すべての DB エラーを catch して握りつぶし
- **防御的すぎるエラーハンドリング** — スキーマで弾けるバリデーションをアプリ層でも再実施、キャッシュミスをエラーとして扱う
- **既存機能の再発明** — UNIQUE 制約があるのにアプリで重複チェック、外部キー制約があるのにアプリで参照整合性チェック
- **起こりえないケースへの対処** — `COALESCE(stock, 0)` を NOT NULL カラムに、内部関数の引数に NULL チェック
- **本番規模軽視** — 数百万行の一括 UPDATE、Scan の多用、`CONCURRENTLY` なしのインデックス追加。開発DBの空テーブルでしか検証していない症状
- **「念のため」過剰設計** — 全カラムにインデックス、全テーブルにソフトデリート、全エンドポイントにキャッシュ。理由を説明できないものは不要
