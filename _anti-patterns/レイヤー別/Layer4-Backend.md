# Layer 4 Backend: アプリケーション — AI実装アンチパターン集

> Layer 4 Backend（[[ルーティングとミドルウェア]] / [[エラーハンドリング]] / [[バリデーション]] / [[認証と認可]] / [[API設計-REST-GraphQL]] / [[データアクセス層]]）の改修で集約された、AIコーディングエージェントが頻発させるアンチパターンの索引。

## このレイヤーで頻出する「AIの癖」

Backend のコードは「**ローカルの単一ユーザでは動くが、本番の同時多リクエスト・攻撃トラフィック・障害シナリオに晒されると壊れる**」コードを AI が量産しやすい。Layer 4 Backend のアンチパターンには次の共通する根がある:

- **「とりあえず全部に適用しておけば安全」誤認** — 認証ミドルウェアのグローバル適用、すべてのハンドラへの try-catch、全フィールドへの NULL チェック。範囲を絞らず全体適用すると、ヘルスチェックやログイン画面まで壊れる、片方を直したつもりで他方が変わる、可読性が壊滅する
- **「フロント検証で十分」「フロントから来る入力は信頼できる」誤認** — バックエンドバリデーション省略、`req.body` をそのまま SQL に埋め込み、トークンを localStorage に保存。**API は誰でも叩ける** という前提が抜ける
- **「とりあえず 200 / とりあえず 500」のステータスコード** — 全エンドポイントで 200 + `{success: false}`、または全エラーを 500 で返す。HTTPセマンティクスを活かせず、リトライ判断・モニタリング・キャッシュが正しく機能しない
- **「エラーを握りつぶす / 詳細を露出する」両極端** — `catch (e) {}` で握りつぶす vs `err.stack` をレスポンスに含める。本来は「**ユーザには汎用メッセージ + requestId、ログには構造化された詳細**」の分離が必要
- **「セキュリティライブラリの誤用」** — JWT 検証で `algorithms` 未指定（alg=none 攻撃）、SHA-256 でパスワードハッシュ、`===` でパスワード比較（タイミング攻撃）、CORS でワイルドカード `*` + `credentials: true`。実装ライブラリは正しいが呼び出し方が脆弱
- **「N+1 / トランザクション欠落の見逃し」** — ORM のループ内クエリ、複数テーブル更新が独立コミット、長時間ロック保持。開発環境では数件のテストデータで顕在化せず、本番で初めて性能・整合性が壊れる
- **「許可リストではなく拒否リスト」設計** — `<script>` を禁止する正規表現、SQLi を防ぐ拒否リスト。バイパス手段が無数にあり、原理的に穴が残る

これらは多くがレイヤー横断のパターン（**過剰なフォールバック / 防御的すぎるエラーハンドリング / 拒否リスト思考 / 本番規模軽視 / 信頼境界の混乱**）に紐付く。

## トピック別アンチパターン索引

### [[ルーティングとミドルウェア]]

| アンチパターン | レビュー観点 |
|---|---|
| 認証ミドルウェアをグローバル適用 | ヘルスチェック・ログインまで保護されてしまう。ルートグループに適用 |
| 動的セグメント (`/users/:id`) を固定セグメント (`/users/new`) より先に定義 | 固定→動的の順、または Radix Tree ルーターを使う |
| 全ハンドラに try-catch を直書き | フレームワーク標準のエラーハンドリング機構に集約 |
| 認証チェックを各ハンドラに直書き | 認証ミドルウェアをルートグループに適用 |
| 過剰なミドルウェアのネスト（10層以上） | 5〜7層に抑える、`next()` の呼び忘れ検出が困難になる |
| リクエストボディの複数回パース | ボディはストリームで一度しか読めない、ミドルウェアで1回 |
| `res.send()` 後に `next()` を呼ぶ | 「Cannot set headers after they are sent」、各枝で `return` |
| キャッチオール `/*` の安易な使用 | SPA フォールバック等、明確な意図がある場合のみ最後に1つ |
| ミドルウェア内で req に大量プロパティを追加 | 暗黙の依存が増える、必要最小限に |

### [[エラーハンドリング]]

| アンチパターン | レビュー観点 |
|---|---|
| `catch (e) {}` でエラー握りつぶし | 障害が見えなくなりデータ不整合の温床。最低でもログ + 再 throw |
| `catch { return [] }` `catch { return null }` でフォールバック値捏造 | エラーは呼び出し元に伝播。フォールバックは要件で明示 |
| 全関数に try-catch を直書き | フレームワーク標準の集約機構に集約 |
| 過剰な防御的コーディング（あらゆる引数に null チェック） | 外部入力のみバリデーション、内部関数は型/スキーマを信頼 |
| スタックトレース・SQL・内部パスをレスポンスに含める | 本番は汎用メッセージ + requestId、詳細はログのみ |
| 全エラーを 500 で返す | エラー型 → HTTPステータスのマッピング表で 4xx/5xx を分ける |
| ユーザー入力をそのままエラーメッセージに含める | Reflected XSS の温床、サニタイズしてから含める |
| 同期 try-catch で Promise/await を捕まえる | `async function` 内 try-catch、または `.catch()` |
| リトライを全エラーで実施 | 5xx と一部 4xx (408/429) のみ、指数バックオフ + ジッター |
| トランザクション内で例外をキャッチして握りつぶし | 必ず再 throw、または明示的にロールバック |

### [[バリデーション]]

| アンチパターン | レビュー観点 |
|---|---|
| 全フィールドに `if (!input.name)` の手書きチェック | スキーマライブラリ（Zod/Pydantic/validator/FormRequest）に集約 |
| 正規表現で SQLi / XSS を防ごうとする | プリペアドステートメント（SQLi）、出力時エスケープ（XSS）で構造的に防ぐ |
| 拒否リスト方式（`'<script>'` を禁止 等） | 許可リスト（列挙値・許可文字の正規表現）に切り替え |
| フロントとバックで同じルールを別実装 | OpenAPI / Zod → 型生成 / GraphQL SDL で単一ソース化 |
| バリデーション失敗で 500 を返す | 422 (Unprocessable Entity) または 400 |
| 最初のエラーで処理を止める | 全フィールドのエラーを一度に返す |
| エラーメッセージにユーザー入力をそのまま含める | Reflected XSS 経路、サニタイズかID参照のみ |
| ビジネスルール検証をスキーマに混ぜる（DB を呼ぶ） | スキーマは純粋な形式検証、ドメイン層に分離 |
| 型さえ付けば検証不要と考える | 実行時バリデーションは別途必須（`JSON.parse` は any） |
| 過度に厳密なメール正規表現 | `@` を含み、ドメインにドット程度 + 確認メール |

### [[認証と認可]]

| アンチパターン | レビュー観点 |
|---|---|
| JWT 検証で `algorithms` オプション未指定 | `alg: none` バイパス。`{ algorithms: ['HS256'] }` を明示 |
| パスワードを SHA-256 / MD5 でハッシュ | bcrypt (cost=12 以上) / Argon2id を使う |
| パスワード比較に `===` / `==` | タイミング攻撃。`bcrypt.compare` / `crypto.timingSafeEqual` |
| パスワードを平文で保存 / ログ出力 | 受信即ハッシュ、ログにも出さない |
| JWT を localStorage / sessionStorage に保存 | XSS 1 発で全トークン窃取。HttpOnly Cookie で保存 |
| Cookie 属性に `Secure` `HttpOnly` `SameSite` のいずれか欠落 | 3 属性すべて必須 |
| 自前で JWT 署名検証を実装 | jose / jsonwebtoken / golang-jwt を使う |
| 認可チェックを各ハンドラに直書き | ミドルウェア / Policy オブジェクトに集約 |
| CRUD 一部だけ認可チェック（典型: 削除が素通し） | 全 CRUD でリソース所有者 / ロールチェック |
| 401 と 403 の混同 / 常に 401 を返す | 未認証=401、認証済み権限不足=403 |
| JWT に個人情報（メール・電話・住所）を詰める | sub に user_id のみ、他は API で取得 |
| アクセストークンを長命にする (24h+) | 短命 (15min) + リフレッシュトークン構成 |
| ログイン失敗時に「ユーザが存在しません」「パスワードが違います」を分けて返す | アカウント列挙攻撃、統一メッセージ |

### [[API設計-REST-GraphQL]]

| アンチパターン | レビュー観点 |
|---|---|
| 全エンドポイントで 200 を返し `{success: false}` でエラー | HTTPステータスを正しく使い分け |
| RPC風URL (`/getUser`, `/createUser`) | リソース名詞 + HTTPメソッド |
| PUT を部分更新に使う | 完全置換は PUT、部分更新は PATCH |
| コレクションエンドポイントにページネーションがない | offset+limit または cursor を最初から組み込み |
| 冗長エンベロープ（`success`, `timestamp`, `version`） | 必要最小限の `{data, meta}` |
| DBカラム名・スタックトレース・SQL をレスポンスに露出 | API Resource / Serializer で整形 |
| GraphQL リゾルバが個別 SQL を発行（N+1） | DataLoader でバッチ化 |
| GraphQL クエリの深さ・複雑度制限なし | depth-limit / cost-analysis でクエリ予算制限 |
| GraphQL スキーマを DB 構造と 1:1 自動生成 | ドメインモデルベースで設計 |
| URL に動詞・認証情報・PII を含める | 認証はヘッダ、PII はボディ |
| 認証エラーを 404 で返す | 401/403/404 を正しく使い分け |
| ネストが深いリソース URL | 2 階層程度、トップレベルリソースに昇格 |
| バージョニング戦略がない | `/v1/` パス or ヘッダで明示 |

### [[データアクセス層]]

| アンチパターン | レビュー観点 |
|---|---|
| ループ内で個別 SELECT を発行（N+1） | Eager Loading (`includes` / `with` / `Preload` / `selectinload`) |
| Eager Loading を `LEFT JOIN` で常に使う | 多数の関連には IN 句方式（`includes` / `selectinload`） |
| `SELECT *` で全カラム取得 | 必要カラムを明示、Index Only Scan を活かす |
| トランザクションなしで複数テーブル更新 | サービス層で `transaction { }` で囲む |
| トランザクション内にユーザー入力待ち・外部 API 待ち | 取得→処理→短いトランザクションで更新の3段に |
| 在庫減・残高減で楽観/悲観ロックを使わない | `lockForUpdate` / `with_for_update` / version カラム |
| NOT NULL カラムへの `COALESCE` / `IFNULL` 防御 | スキーマを信頼、NULL 許容カラムだけ |
| 全モデルへのリポジトリパターン適用 | テスタビリティ / データソース切替が必要な場合のみ |
| ORM の自動マイグレーションを本番で使う | 開発時のみ、本番は migration ファイル |
| ループで `model.save` を呼ぶ | `bulkCreate` / `insert_all` / `createMany` / COPY |
| 巨大テーブルの `findAll()` をページネーションなしで | カーソル / offset+limit / `find_each` |
| プレースホルダ上限を超える IN 句 | バッチ分割または COPY/LOAD DATA |
| 複雑な集計を ORM で無理に表現 | ウィンドウ関数・再帰 CTE は生 SQL |
| 文字列結合での動的 WHERE | クエリビルダの条件分岐 API か Query Object |

## レイヤー横断の癖（Layer 4 Backend で目立つもの）

### 「念のため全部適用」誤認
- 認証ミドルウェアのグローバル適用 → ヘルスチェック・ログインも保護してしまう
- 全ハンドラへの try-catch → 集約エラーハンドリングの利点を消す
- 全フィールドへの NULL チェック → スキーマ保証を活かせない、可読性壊滅
- 全レスポンスを `{success, data, timestamp, version}` でラップ → サイズ膨張、契約変更の波及

### 「とりあえず 200 / とりあえず 500」
- 成功も失敗も 200、ボディの `success` で判別 → リトライ・キャッシュ・モニタリングが壊れる
- バリデーション失敗・認可失敗も 500 → アラート S/N 比悪化、リトライ戦略破綻
- 401 と 403、422 と 400、404 と 403 の混同

### 「捨てるか晒すか」両極端
- `catch (e) {}` で握りつぶし → 障害可視性ゼロ
- `err.stack` `err.sql` をレスポンスに含める → 内部実装漏洩
- 正解は「ユーザに汎用 + requestId、ログに構造化詳細」の分離

### 「セキュリティライブラリの誤用」
- JWT 検証で `algorithms` 省略 → `alg: none` バイパス
- パスワードに SHA-256 + ソルトなし → GPU でブルートフォース
- `===` でパスワード比較 → タイミング攻撃
- CORS で `*` + `credentials: true` → 仕様上禁止だが見落とし
- localStorage にトークン → XSS 1 発で全奪取

### 「N+1 / トランザクション境界の見逃し」
- ORM のループ内クエリ
- 複数テーブル更新を独立した execute で実行（途中失敗で不整合）
- ユーザー入力待ちをトランザクション内に含めて長時間ロック
- 在庫減・残高減でロックを取らない、レースコンディション

### 「許可リスト vs 拒否リスト」誤選択
- `<script>` 拒否で XSS を防ごうとする → バイパス無数
- `select|drop|union` 拒否で SQLi を防ごうとする → 正当英文も弾く、バイパス可
- 正解はプリペアドステートメント（SQLi）、出力時エスケープ（XSS）、許可リスト（バリデーション）
