# Layer 7: 設計・アーキテクチャ — AI実装アンチパターン集

> Layer 7（[[関心の分離]] / [[SOLID原則]] / [[モノリスvsマイクロサービス]] / [[CI-CD]] / [[テスト戦略]] / [[イベント駆動-CQRS]]）の改修で集約された、AIコーディングエージェントが頻発させるアンチパターンの索引。

## このレイヤーで頻出する「AIの癖」

Layer 7 は **「AI が『綺麗な設計』として真っ先に提案する形が、実プロジェクトでは過剰設計になる**」レイヤーで、レイヤー分割 / インターフェース化 / マイクロサービス化 / CQRS 化 / テストカバレッジを **「やればやるほど良い」** 方向に倒す。Layer 7 アンチパターンには次の 7 つの根がある。

- **「綺麗な階層化への偏愛」** — 単純な CRUD にも Controller / Service / Repository / DAO / Entity の 5 層を構築する。各層がパススルーになり、変更が複数ファイルにまたがる**ショットガン手術**を招く。AI は教科書的な階層化を「ベストプラクティス」と認識する
- **「インターフェース爆発」** — 1 実装 1 インターフェースを機械的に生成し、`UserService` / `UserServiceImpl` のような無意味な二重化が発生する。**交換可能性が必要な場合のみ**インターフェースを作る原則が抜ける
- **「分割優先のバイアス」** — モノリスを「即マイクロサービス化」、CRUD を「即 CQRS 化」、関数を「即クラス分離」と提案する。**「今分離すべきか、まだ早いか」**の文脈判断が抜け、ドメイン境界が固まる前の早すぎる分割で**境界の修正コスト**を膨大にする
- **「Happy Path のみ」** — テスト・サービス間通信・イベントハンドラいずれも正常系のみを生成し、**異常系（タイムアウト / リトライ / 重複配信 / 例外時のロールバック）**が抜ける。本番障害は境界・異常系に集中するため、検出力が大きく劣化
- **「実装の詳細をテストする」** — モックだらけのテスト、private メソッド直接テスト、`toHaveBeenCalledTimes(3)` のような呼び出し回数検証が混入。**振る舞いではなく実装に密結合したテスト**で、リファクタごとに大量に壊れる
- **「動かすための便宜」漏出** — 開発時の `--no-verify`、CI のシークレットハードコード、`npm install`（lockfile 無視）、`latest` タグ、`Allow-Origin: *`、retry 3 でフレイキー隠蔽。**AI は動かすことを最優先**で、本番運用に耐える堅牢性が抜ける
- **「CRUD 命名の温存」** — イベント命名で `OrderUpdated` `UserCreated` のような CRUD 直訳を生成する。**ドメインの意味（OrderPlaced / UserEmailVerified）**が消え、イベント駆動の利点（ドメイン意図の伝達）が失われる

これらは多くがレイヤー横断のパターン（**過剰なフォールバック / 防御的すぎるエラーハンドリング / 不要な抽象化 / 既存ユーティリティの再発明**）に紐付く。Layer 7 は特に **「綺麗な設計」と「実プロジェクトに合った設計」の境界** を厳密に管理する必要がある。

## トピック別アンチパターン索引

### [[関心の分離]]

| アンチパターン | レビュー観点 |
|---|---|
| 過剰なレイヤー分割（Controller / Service / Repository / DAO 全層） | 各層に固有のロジックがあるか、3 層全てが 1 行のメソッドならパススルー候補 |
| 儀式的なインターフェース | 「今交換する計画があるか / テストでモックするか」の 2 条件以外は作らない |
| 技術分割の過信（`models/` `views/` `controllers/`） | ドメイン分割（`User/` `Order/`）に変えて変更を局所化する |
| 共通化の過剰追求（偶然の重複 = 本質的重複） | Rule of Three（3 回以上完全に同じ重複が出るまで共通化しない） |
| 横断関心事のコピペ展開 | ミドルウェア / デコレータ / AOP に移譲、宣言的に適用 |
| ショットガン手術の温存 | 「1 つの変更で複数ファイル修正なら分離の軸が間違っている」を AI への指示に明記 |
| God Object / God Module | 「Utils」「Helper」「Manager」命名のクラス肥大化を疑う |
| Feature Envy（他モジュールのデータに頻繁にアクセス） | データを持っている側にロジックを移す（[[デメテルの法則]]） |

### [[SOLID原則]]

| アンチパターン | レビュー観点 |
|---|---|
| 全クラスにインターフェース自動生成 | 命名 `XxxImpl` パターンは削除候補 |
| Abstract Factory の過剰適用 | `new` で十分な場面はファクトリ不要 |
| 全メソッドに try-catch | 例外処理の責務を Controller / ミドルウェアに集約 |
| 依存注入チェーンが深すぎる（5 層以上） | パススルー中間層を削除 |
| 上位モジュール内での `new` 直書き | コンストラクタ引数で受け取る（DIP） |
| 巨大 Repository インターフェース（`find` `save` `delete` `bulkUpdate` ...） | `UserReader` / `UserWriter` に分離（ISP） |
| シングルトン乱用での隠れ依存 | DI コンテナのスコープ管理で「インスタンス 1 つ」を実現 |
| 継承による共通化（LSP 違反予備軍） | 委譲（コンポジション）を優先 |
| `Square extends Rectangle` 系の振る舞い不互換継承 | `is-a` だけでなく事前条件・事後条件・不変条件の互換性を確認 |

### [[モノリスvsマイクロサービス]]

| アンチパターン | レビュー観点 |
|---|---|
| 初期段階でのマイクロサービス設計 | モノリス or モジュラーモノリスで開始、痛みが出てから分割 |
| 全通信を REST API に | 同期が必要な箇所のみ REST、それ以外はイベント駆動 |
| サービスごとに異なるフレームワーク | 「選択できる」と「選択すべき」を区別、明確な理由がなければ統一 |
| 共通ライブラリの密結合 | 共通化は最小限、バージョン互換性を慎重に管理 |
| 共有データベース | サービスごとに DB、共有は API / イベント経由 |
| サーキットブレーカー欠如 | 全サービス間呼び出しにタイムアウト + サーキットブレーカー |
| 分散トランザクションでの 2PC | Saga パターン or 結果整合性を許容する設計 |
| サービスごとの認証ロジック分散 | ID プロバイダー（Auth0 等）に集約、サービスは JWT 検証のみ |
| 同期 HTTP の連鎖（A→B→C→D） | 可用性が積算（99.9%^4 ≈ 99.6%）、非同期に置き換え |
| Eloquent Model / Entity の境界漏れ | DTO / 公開契約で必ず変換 |

### [[CI-CD]]

| アンチパターン | レビュー観点 |
|---|---|
| 全テストを 1 ジョブで直列実行 | テストを並列化、段階的実行 |
| シークレットのハードコード | `secrets.X` 経由のみ、リテラル禁止、漏洩時は即ローテーション |
| 過剰なパイプライン通知 | 失敗時のみ通知、成功はダッシュボード |
| 本番と異なる CI 環境（CI が SQLite / 本番 PostgreSQL） | `services:` で本番同型コンテナを使用 |
| `--no-verify` / hook バイパス | hook 失敗は根本原因を直す、AI 生成スクリプトで grep 確認 |
| キャッシュキー不適切 | `hashFiles('**/package-lock.json')` で依存ファイルハッシュを含める |
| マイグレーションを CD パイプライン外で手動実行 | パイプラインに `migrate` を組み込み、後方互換マイグレーション順序を遵守 |
| 失敗時の自動ロールバックなし | ヘルスチェック失敗で自動ロールバック、ECS / k8s の rollback 機能 |
| イメージタグに `latest` のみ | コミット SHA / semver タグで追跡可能に |
| `npm install`（lockfile 無視） | `npm ci`（決定的インストール）に変更 |
| タイムアウト未設定（永久実行リスク） | `timeout-minutes:` を設定 |

### [[テスト戦略]]

| アンチパターン | レビュー観点 |
|---|---|
| 全メソッドに 1 対 1 でテスト生成 | 公開インターフェースの振る舞い単位に変更 |
| モックだらけのユニットテスト | 境界（外部 API / DB）のみモック、内部は Fake / 実物 |
| テスト名が `test1`, `test2` | `should_<期待結果>_when_<前提>` で振る舞い記述 |
| Happy path のみテスト生成 | 異常系・境界値（空配列 / null / 0 / 上限値）を必ず含める |
| 共有フィクスチャの使い回し | `beforeEach` でテストごとにクリーンセットアップ |
| 順序依存のテスト | 各テストは独立、並列実行で破綻しない |
| カバレッジ追求でアサーションなし | 各テストに意味のある `expect()` / `assert` を必須化 |
| フレイキーテストを `retry: 3` で誤魔化す | 真因を特定して修正、retry は最終手段 |
| 実 DB を使わずに ORM の SQL 生成だけテスト | Integration テストで実 DB（PostgreSQL コンテナ）を使う |
| 内部呼び出し回数を検証（`toHaveBeenCalledTimes(3)`） | 入力 → 出力の振る舞いを検証 |
| private メソッド直接テスト | public インターフェースの振る舞いから検証 |

### [[イベント駆動-CQRS]]

| アンチパターン | レビュー観点 |
|---|---|
| 全 API を CQRS 化 | 読み書きの非対称性が実痛になっている箇所のみ適用 |
| CRUD イベント（`UserCreated` / `Updated` / `Deleted`） | ドメイン言語（`UserEmailVerified` `AccountSuspended`）で命名 |
| イベントハンドラに複雑なロジック | ハンドラはドメインサービスへの委譲のみ |
| 非同期処理の例外を握りつぶす | DLQ に退避、監視・リトライ・通知に繋ぐ |
| べき等性のないハンドラ | イベント ID + ハンドラ名で `processedEvents` を保持し重複検出 |
| 巨大イベント（`data: order` で全体送信） | ID + 必要最小限のフィールドのみ、詳細は API で取得 |
| イベントの双方向依存（A↔B 循環購読） | 依存方向を一方向に限定、共通上流から両者が分岐 |
| アウトボックスパターン未使用 | DB + outbox を 1 トランザクション、別ワーカーがイベント発行 |
| 同期 HTTP との混在で複雑化 | 通信ごとに「同期 / 非同期」を明確に決定 |
| 全システムを一気に CQRS 化 | 段階導入（コードレベル → 読み取りレプリカ → 完全分離） |

## 横断テーマ別

Layer 7 のアンチパターンは、レイヤー横断の 4 大パターンと密接に紐付く。横断パターン別の整備（`_anti-patterns/パターン別/`）を Week 11 で行う予定。

### 過剰なフォールバック

- 全メソッドに try-catch
- 例外を握りつぶすイベントハンドラ
- 「念のため」の `?? null` `|| {}`
- フレイキーテストの `retry: 3` 誤魔化し

### 防御的すぎるエラーハンドリング

- 内部関数の引数チェック（型システムが既に保証）
- 起こりえないケースへの対処
- 全メソッドにバリデーション

### 不要な抽象化

- 1 実装 1 インターフェース
- 過剰なレイヤー分割（パススルー層）
- Abstract Factory の過剰適用
- 早すぎるマイクロサービス化 / CQRS 化
- 「将来の拡張」のためのフック

### 既存ユーティリティの再発明

- プロジェクト内の既存サーキットブレーカー / リトライ実装を見ずに自前実装
- 既存のミドルウェア / デコレータ機構を使わずに各 Controller に処理を直接コピペ
- 既存の Fake Repository を使わずに毎テストでモックを構築
