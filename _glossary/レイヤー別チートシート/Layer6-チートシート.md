# Layer 6: セキュリティ — チートシート

> **このファイルは何か:** Layer 6（セキュリティ）の **「再読時に1分で思い出すための要約」**。XSS / CSRF / SQLi / CORS / DDoS / 最小権限 / サプライチェーンを1ページに集約。

## レイヤーの位置

> **悪意のある攻撃**からシステムとユーザーを守る。
> セキュリティは **全レイヤーに横断的に関わる**。Layer 6 は「主要な攻撃と防御の地図」。

## 防御の3層構造

```mermaid
flowchart TD
    A[多層防御 (Defense in Depth)]
    A --> B[層1: 入力境界<br/>バリデーション / 許可リスト / レート制限]
    A --> C[層2: 構造的防御<br/>プリペアド / 出力エスケープ / CSP / SameSite]
    A --> D[層3: 出力境界<br/>最小情報露出 / 構造化ログ / 詳細はサーバ内のみ]
```

**1つの層に頼らず、3層が直交していると強い。** AI 生成コードは層1だけで終わりがち。

## 攻撃と対策のマッピング

| 攻撃 | 入る場所 | 効く対策 | 効かない対策 |
|---|---|---|---|
| **XSS (反射型)** | クエリパラメータ / フォーム | 出力時エスケープ / CSP | 入力時の `<script>` 拒否 |
| **XSS (DOM-based)** | `innerHTML` / `eval` | テキスト挿入のみ / textContent | サーバ側 escape |
| **CSRF** | Cookie 自動送信 | SameSite=Lax/Strict + CSRFトークン | リファラチェック単独 |
| **SQLi** | クエリパラメータ / フォーム | プリペアドステートメント | `'` のエスケープのみ |
| **コマンドインジェクション** | OS コマンド呼び出し | パラメータ化実行 / シェル不経由 | `;` 拒否 |
| **オープンリダイレクト** | リダイレクト URL | 許可リスト / 相対 URL のみ | URL の "http" チェック |

## Cookie 設定の必須3属性

```
Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Lax; Path=/
```

| 属性 | 効果 | 欠けると |
|---|---|---|
| `Secure` | HTTPS でのみ送信 | 中間者でCookie取得 |
| `HttpOnly` | JS から読めない | XSS でトークン窃取 |
| `SameSite` | 第三者サイトに送信しない | CSRF 攻撃 |

**3つ全て必須。** AI に Cookie 生成を頼むときは必ず 3 属性を指定する。

## 認証・認可のステータスコード

| コード | 意味 | 使う場面 |
|---|---|---|
| 401 Unauthorized | 未認証 / 認証失敗 | トークンなし / 期限切れ |
| 403 Forbidden | 認証済みだが権限なし | 他者のリソースにアクセス |
| 404 Not Found | リソースなし | ※ 存在隠蔽用に 403→404 する判断もある |

**「全部 401 を返す」「全部 403 を返す」**は AI の典型。**「ログイン失敗時にユーザの存在を漏らさない」**ためにわざと 401 で統一する設計判断もあり、ここはチームの方針が必要。

## DDoS 対策の多層

| 層 | 対策 | 主体 |
|---|---|---|
| エッジ | CDN / Cloudflare / AWS Shield | 外部サービス |
| LB | レート制限 / コネクション制限 | インフラ |
| API GW | APIキー単位レート制限 | アプリ近接 |
| アプリ | 認証ユーザ単位スロットリング | アプリ内 |

**1層だけでは不十分。** 体積攻撃はエッジで、アプリ層攻撃は API GW で、ビジネスロジック攻撃はアプリで対処。

## 最小権限の原則のチェック

- データベース接続ユーザは **必要なテーブル・操作のみ**（`SELECT` / `INSERT`）
- IAM ロールは **必要な API のみ** (`s3:GetObject` のみ等)
- コンテナは **非 root ユーザ**で実行
- 環境変数のシークレットは **必要なコンテナのみ**

**「全権限を付けて動かしてから減らす」**は減らされない。最初から必要最小限で構築。

## サプライチェーンの防御

- `package-lock.json` / `Gemfile.lock` / `poetry.lock` をコミットして再現性確保
- バージョン pinning（`^1.2.3` ではなく `1.2.3`）
- npm install ではなく **`npm ci`** (lockfile 厳守)
- SBOM (Software Bill of Materials) 生成
- `npm audit` / `dependabot` / `renovate` で脆弱性監視

## AI協働でよく出るアンチパターン (Layer 6)

- **拒否リスト方式** (`<script>` を弾く / `'select|drop|union'` を弾く) → 原理的にバイパス可能
- **JWT 検証で `algorithms` 未指定** → `alg: none` バイパス
- **パスワードを SHA-256 / `===` で比較** → bcrypt + timingSafeEqual
- **JWT を localStorage に保存** → XSS で全奪取 → HttpOnly Cookie へ
- **CORS で `Access-Control-Allow-Origin: *` + credentials** → 仕様違反
- **エラーメッセージにスタックトレース / SQL** → 内部実装漏洩
- **ログイン失敗で「ユーザ存在しません」「パスワード違います」を分けて返す** → アカウント列挙

詳細: [[_anti-patterns/レイヤー別/Layer6|Layer 6 アンチパターン集]]

## 「これだけ AI に伝える」プロンプト雛形

```
前提:
- 認証方式: Cookie + Session / JWT / OAuth 2.0
- フロントは SPA / SSR / 通常のフォーム POST
- 想定脅威モデル: <信頼境界、想定攻撃者>

やってほしいこと: <処理内容>

制約 (セキュリティ要件):
- 入力は許可リスト方式でバリデーション (拒否リスト禁止)
- SQL は必ずプリペアドステートメント
- 出力は必ずエスケープ (テンプレートエンジンの自動エスケープを使う)
- Cookie は Secure + HttpOnly + SameSite=Lax 必須
- パスワードは bcrypt (cost ≥ 12) または Argon2id
- JWT は algorithms 明示、有効期限 ≤ 15min + リフレッシュ
- エラーメッセージにスタックトレース・SQL・内部パスを含めない
- ログイン失敗メッセージは統一 (アカウント列挙対策)

判断基準:
- 上記のチェックを `/anti-pattern-scan` で確認
- セキュリティテストケース (SQLi / XSS / CSRF) を含める
```
