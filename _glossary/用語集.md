# 用語集 v1 — 初学者が詰まりやすい用語の最低限辞書

> **このファイルは何か:** 本教材を読んでいて「この単語、分かったつもりで読み飛ばしているな」と思ったら立ち止まる用辞書。**初学者が詰まりやすい用語**を中心に約45語を厳選した。
>
> 各エントリは **「1行定義」+「もう一歩」+「関連トピック」** の3点セット。1行定義だけでも読める設計。

## 使い方

- 教材を読んでいて引っかかった単語をここで引く
- 「もう一歩」まで読むと、**なぜその概念が必要か** が分かる
- 「関連トピック」で本格的なトピック解説に飛ぶ
- 用語の **初出はトピック内で必ず説明される** 設計だが、忘れたときの再確認用にここを使う
- まだ載っていない用語は `/glossary` skill で追加できる

## HTTPと通信

### ステートレス
**1行定義:** サーバが過去のリクエストを覚えていない通信モデル。
**もう一歩:** 「あなたが誰か」を毎回送る必要がある（Cookie / Authorization ヘッダ）ため、後続のセッション管理・CSRF・JWT の存在理由になる。
**関連:** [[HTTP-HTTPS]] / [[認証と認可]]

### 冪等 (べきとう / idempotent)
**1行定義:** 何度実行しても結果が同じになる性質。
**もう一歩:** GET / PUT / DELETE は冪等、POST は非冪等。HTTP リトライ判断の根拠であり、イベント駆動の重複配信耐性の核。AI に「リトライを追加して」と頼む前に、この処理は冪等かを確認する。
**関連:** [[HTTP-HTTPS]] / [[イベント駆動-CQRS]]

### プリフライト
**1行定義:** クロスオリジン要求の前に CORS 許可を確認する OPTIONS リクエスト。
**もう一歩:** 「単純リクエスト」以外（PUT / DELETE / カスタムヘッダ等）で発生。CORS 設定不備のフロント症状の典型原因。
**関連:** [[CORS]]

### TTL (Time To Live)
**1行定義:** データの有効期限。
**もう一歩:** DNS では「IP を何秒キャッシュしてよいか」、Redis では「キーが何秒で消えるか」、CDN では「エッジに何秒残すか」。**短すぎると負荷、長すぎると古いデータ問題**。
**関連:** [[DNS]] / [[キャッシュ戦略]] / [[CDN]]

### TLSハンドシェイク
**1行定義:** クライアントとサーバが暗号鍵を確立する初回交換。
**もう一歩:** TLS 1.3 で 1-RTT、QUIC で 0-RTT に短縮。**新規接続が遅い症状**は大抵ここ。Keep-Alive で再利用するのが基本。
**関連:** [[TLS-SSL]] / [[HTTP-HTTPS]]

## 認証・認可

### 認証 (Authentication)
**1行定義:** 「あなたは誰か」を確認する処理。
**もう一歩:** ログイン・JWT 発行・パスワード検証はすべて認証。**認可と混同するとセキュリティホール**になる。
**関連:** [[認証と認可]]

### 認可 (Authorization)
**1行定義:** 「あなたは何をしてよいか」を判断する処理。
**もう一歩:** 「ログインしているから何でもできる」は誤り。**「自分のリソースしか触れない」「管理者でないと削除できない」** がここで決まる。AI に頼むと CRUD の一部（特に削除）の認可チェックを忘れがち。
**関連:** [[認証と認可]] / [[最小権限の原則]]

### JWT (JSON Web Token)
**1行定義:** 署名付きの JSON で、認証情報を表すトークン形式。
**もう一歩:** `header.payload.signature` の3部構成。**改ざん検知はできるが暗号化ではない** ので payload は誰でも読める。`alg: none` 攻撃 / 長すぎる有効期限 / payload に PII が典型的アンチパターン。
**関連:** [[認証と認可]]

### セッション
**1行定義:** ステートレスな HTTP に「一連の会話」を持たせる仕組み。
**もう一歩:** サーバに状態を持つ「セッションストア方式」と、トークン（JWT）に持たせる「ステートレス方式」がある。**スケーラビリティ vs 失効容易性** のトレードオフ。
**関連:** [[認証と認可]]

### CSRF (Cross-Site Request Forgery)
**1行定義:** ブラウザが Cookie を自動送信する性質を悪用する攻撃。
**もう一歩:** 攻撃者が「悪意のあるサイト」からユーザの認証付きで自サイトにリクエストを送らせる。**SameSite=Lax/Strict + CSRFトークン** で防ぐ。
**関連:** [[CSRF]]

### XSS (Cross-Site Scripting)
**1行定義:** ユーザ入力が HTML / JavaScript として解釈される攻撃。
**もう一歩:** 反射型・蓄積型・DOM ベースの3種。**出力時のエスケープ + CSP** で防ぐ。`<script>` を拒否リストで弾く実装は穴だらけ。
**関連:** [[XSS]]

### SameSite
**1行定義:** Cookie がクロスサイトリクエストで送信されるかを制御する属性。
**もう一歩:** `Strict` / `Lax` / `None` の3値。デフォルトは Lax（最近のブラウザ）。**CSRF 防御の第一線** だが Lax でも GET 経由攻撃は防げないので CSRFトークンと併用。
**関連:** [[CSRF]] / [[CORS]]

### HttpOnly
**1行定義:** JavaScript から Cookie を読めなくする属性。
**もう一歩:** XSS が発生した時の **トークン窃取防止** に必須。逆に言うと localStorage のトークンは XSS 1 発で全奪取される。
**関連:** [[XSS]] / [[認証と認可]]

## データベース

### ACID
**1行定義:** トランザクションの4性質（原子性・一貫性・分離性・耐久性）の頭文字。
**もう一歩:** RDB の信頼性の核。**分離レベル (Isolation Level)** だけは設定により挙動が変わるので、AI が生成したコードの分離レベルを確認する。
**関連:** [[トランザクション]] / [[RDB]]

### トランザクション
**1行定義:** 「全部成功するか、全部失敗するか」をまとめた処理単位。
**もう一歩:** 複数テーブル更新が独立コミットされていると、途中失敗で **データ不整合** になる。**境界の引き方**（どこから始まりどこで終わるか）が設計判断。
**関連:** [[トランザクション]]

### 楽観ロック / 悲観ロック
**1行定義:** 楽観 = 更新時に競合を検出してリトライ、悲観 = 取得時にロックして他者を待たせる。
**もう一歩:** 在庫減・残高減のような **Read-Modify-Write** で必須。**どちらも使わない**と、同時アクセスで在庫がマイナスになる。AI 生成コードはここを忘れがち。
**関連:** [[トランザクション]] / [[並行性の基本概念]]

### N+1
**1行定義:** 1回の SELECT で取った N 行に対して、関連を取るために N 回追加クエリを発行する問題。
**もう一歩:** ORM のループ内 `.posts` アクセスで頻発。**Eager Loading** (`includes` / `with` / `Preload` / `selectinload`) で1〜2クエリに削減。**開発環境では数件のテストデータで顕在化せず、本番で初めて発覚**するのが恐ろしい。
**関連:** [[データアクセス層]]

### インデックス
**1行定義:** 大量データから高速に検索するためのデータ構造（多くは B-Tree）。
**もう一歩:** **読み込み高速化と書き込みコスト** のトレードオフ。複合インデックスは **「カラム順」** が重要（左から使われる）。
**関連:** [[Resources/Study/Layer3-データ永続化/インデックス|インデックス]] / [[ハッシュテーブル]]

### レプリカ遅延
**1行定義:** プライマリ DB の更新がレプリカに反映されるまでのラグ。
**もう一歩:** 通常はミリ秒〜数秒。「**書いた直後の自分への表示**」をレプリカから読むと、まだ反映されていないことがある。書き込み直後の読みはプライマリから、または セッションスティッキー。
**関連:** [[RDB]] / [[NoSQL]]

## 並行性

### 競合状態 (Race Condition)
**1行定義:** 複数の処理が同じデータを同時に触り、実行順序で結果が変わる現象。
**もう一歩:** 「**残高チェック → 引き落とし**」の2ステップで、間に他のリクエストが入ると残高がマイナスになる。**アトミック操作 / ロック / トランザクション** で防ぐ。
**関連:** [[並行性の基本概念]] / [[トランザクション]]

### デッドロック
**1行定義:** 複数のロックが互いの解放を待ち合って永久に進まない状態。
**もう一歩:** A→B 順と B→A 順でロックを取る関数が同時実行されると発生。**ロック取得順序を統一** すれば防げる。
**関連:** [[並行性の基本概念]]

### べき等性 (Idempotency)
**1行定義:** 何度実行しても結果が同じになる性質（→ 冪等と同義）。
**もう一歩:** イベント駆動・リトライ・分散システムの根本要件。**「べき等キー」** をクライアントが付与し、サーバが重複検知する設計が定石。
**関連:** [[イベント駆動-CQRS]] / [[HTTP-HTTPS]]

### アトミック
**1行定義:** 「途中状態が観測されない」操作。
**もう一歩:** CPU のアトミック命令（CAS）、DB の単一行更新、Redis の `INCR` など。**並行性問題の解決手段の最小単位**。
**関連:** [[並行性の基本概念]]

## 計算量

### O(1)
**1行定義:** 入力サイズに関わらず一定時間。
**もう一歩:** ハッシュテーブルの参照、配列のインデックスアクセス。**「N=100万でも一瞬」** の感覚。
**関連:** [[計算量-BigO]] / [[ハッシュテーブル]]

### O(n)
**1行定義:** 入力サイズに比例した時間。
**もう一歩:** 配列の線形探索、リストの全走査。N=100万で「一瞬」だが、ループの中で O(n) を呼ぶと O(n²) で爆発する。
**関連:** [[計算量-BigO]]

### O(log n)
**1行定義:** 入力が倍になっても定数時間しか増えない。
**もう一歩:** 二分探索、B-Tree のインデックス検索。N=10億でも約30回程度。**インデックスがなぜ高速か** の根拠。
**関連:** [[計算量-BigO]] / [[Resources/Study/Layer3-データ永続化/インデックス|インデックス]]

### 償却計算量 (Amortized)
**1行定義:** 一連の操作の平均で見た計算量。
**もう一歩:** 動的配列の `push` は通常 O(1) だが、たまに O(n) のリサイズが入る。平均すると O(1)。「**最悪ケースは怖いが平均は速い**」を数学的に正当化する概念。
**関連:** [[計算量-BigO]] / [[データ構造とアルゴリズム]]

## 設計

### 関心の分離 (Separation of Concerns)
**1行定義:** 変更の理由が異なるものは別の場所に置く設計原則。
**もう一歩:** 全設計原則の根本。「**1つの変更で複数ファイルを修正している**」と感じたら、分離の軸が間違っている可能性。
**関連:** [[関心の分離]] / [[SOLID原則]]

### DIP (Dependency Inversion Principle)
**1行定義:** 上位モジュールが下位モジュールの具体ではなく抽象に依存する原則。
**もう一歩:** SOLID の D。**テスタビリティ・差し替え可能性** に直結。AI は機械的に「全クラスにインターフェース」と提案するが、**「今交換する計画があるか / テストでモックするか」** の2条件以外は不要。
**関連:** [[SOLID原則]]

### DI (Dependency Injection)
**1行定義:** 依存オブジェクトを外部から渡す設計手法。
**もう一歩:** DIP を実現する具体テクニック。**コンストラクタ DI / セッタ DI / メソッド DI** がある。Spring / NestJS / .NET の DI コンテナはこの自動化。
**関連:** [[SOLID原則]]

### インターフェース
**1行定義:** 「何ができるか」だけ定義し、具体実装は別に置く契約。
**もう一歩:** Java/C#/TypeScript の `interface`、Go の `interface`、Python の Protocol。**1実装1インターフェースは過剰**で、`UserService` / `UserServiceImpl` のような無意味な二重化を生む。
**関連:** [[SOLID原則]] / [[関心の分離]]

### 結合度・凝集度
**1行定義:** 結合度 = モジュール間の依存の強さ、凝集度 = モジュール内の関連の強さ。
**もう一歩:** **「結合度は低く、凝集度は高く」** が良い設計。「Utils」「Helper」のような命名は凝集度が低い兆候（複数の異なる責務が混在）。
**関連:** [[関心の分離]] / [[SOLID原則]]

### DTO (Data Transfer Object)
**1行定義:** 層の境界をまたぐ際にデータをまとめる単純なオブジェクト。
**もう一歩:** **DB エンティティをそのまま API レスポンスに返さない** ためのバッファ。内部構造変更を外部契約に伝播させない。
**関連:** [[API設計-REST-GraphQL]] / [[関心の分離]]

## 運用

### SLA (Service Level Agreement)
**1行定義:** ユーザに対する **契約上の品質約束**（例: 99.9% 稼働率）。
**もう一歩:** 違反すると返金・契約解除等のペナルティ。SLO はその内部目標、SLI は実測指標。
**関連:** [[モニタリング]]

### SLO (Service Level Objective)
**1行定義:** SLA を守るための **内部目標**。
**もう一歩:** 「99.95% 稼働を目指す」のように、SLA より厳しく設定。**エラーバジェット** = 100% - SLO で、リスクのある変更をどれだけ許容できるかを管理する。
**関連:** [[モニタリング]] / [[CI-CD]]

### p99 (99パーセンタイル)
**1行定義:** リクエストの 99% がこの値以下に収まる、という閾値。
**もう一歩:** 平均値ではなく分布の **裾** を見る指標。ユーザの 1% が「めっちゃ遅い」と感じている問題は平均値では見えない。p50 (中央値) と p99 のギャップを見るのが基本。
**関連:** [[モニタリング]] / [[パフォーマンス最適化]]

### フレイキーテスト (Flaky Test)
**1行定義:** 同じコードでも実行ごとに通ったり失敗したりするテスト。
**もう一歩:** 順序依存・時刻依存・非同期処理の `await` 漏れ・共有リソースの競合が原因。**`retry: 3` で誤魔化さず、真因を特定**するのが鉄則。
**関連:** [[テスト戦略]]

### サーキットブレーカー (Circuit Breaker)
**1行定義:** 連続失敗時に呼び出しを一時停止し、障害を伝播させない仕組み。
**もう一歩:** Open / Half-Open / Closed の3状態。**マイクロサービス間呼び出し / 外部 API 呼び出しに必須**。リトライだけだと障害サービスを攻撃する形になる。
**関連:** [[モニタリング]] / [[非同期処理とメッセージキュー]]

## AI協働

### ハルシネーション (Hallucination)
**1行定義:** AI が **事実でない情報を自信満々に生成する**現象。
**もう一歩:** 存在しない API、間違ったライブラリ仕様、誤った計算量主張。AI 出力は **必ず一次情報 (公式ドキュメント / コードベース) で検証** する。
**関連:** [[_starter/04_AI協働の基本動作]]

### プロンプト
**1行定義:** AI への指示文。
**もう一歩:** **前提・やってほしいこと・制約・判断基準** を明示するほど精度が上がる。各トピックの「効くプロンプトの型」がテンプレ。
**関連:** [[_starter/04_AI協働の基本動作]]

### コンテキスト
**1行定義:** AI が一度に「考慮できる」入力の総量。
**もう一歩:** モデルごとにコンテキスト長 (例: 200K / 1M トークン) が決まっている。**長すぎるとトークン代が高くつき、関連箇所への注意が薄れる**。
**関連:** [[_starter/04_AI協働の基本動作]]

### トークン
**1行定義:** AI の入出力単位（おおよそ単語の一部 〜 1単語）。
**もう一歩:** 日本語は英語よりトークン消費が多め。コードはコメント・空白を含めて全部トークン化される。**コスト・速度・精度** すべてに影響。
**関連:** [[_starter/04_AI協働の基本動作]]

### プロンプトインジェクション
**1行定義:** ユーザ入力が AI への命令として解釈されてしまう攻撃。
**もう一歩:** 「以前の指示を無視して...」のような文字列を含むユーザ入力で AI を乗っ取る。**信頼境界の混乱** という意味で SQLi / XSS と同じ構造。
**関連:** [[_starter/04_AI協働の基本動作]] / [[XSS]]
