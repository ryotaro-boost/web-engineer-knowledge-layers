# AIコーディング時代の学び方

> **このファイルは何か:** 本教材を貫く前提認識。「コードを書ける」ことではなく **「AIが書いたものを判断できる」** ことを学ぶ場として、教材をどう使うかを示す。

## 前提認識: 何が変わったか

コーディング作業そのものは、AIコーディングエージェント（Claude Code, Cursor, Copilot 等）が大半を担うようになった。これは「楽になった」ではなく、**エンジニアに求められるスキルの構造が変わった**ということ。

### スキル比重の変化

| スキル | 以前 | これから |
|--------|------|---------|
| 設計判断を下す（何を作るか / どの技術で作るか / トレードオフ） | 中 | **大** |
| AIレビュー力（生成物の誤り・過剰設計・セキュリティリスクを見抜く） | — | **大** |
| 症状→原因の追跡力（「動かない」から根本原因まで辿る） | 中 | **大** |
| システム俯瞰力（レイヤー間の接続点を把握する） | 中 | **大** |
| コードを書ける | 大 | 中（AIへの指示の前提として必要） |
| ライブラリの使い方を覚える | 大 | 小（AIが知っている） |

「コードを書ける」が小さくなったわけではない。**AIに何を書かせ、出力を判断するために、コードを読み書きできる前提は依然必要**。ただ、それが**目的ではなく手段**になった。

## 本教材の構造との対応

各トピックドキュメントは、上記4スキルを養うように構造化されている:

| ドキュメント要素 | 養うスキル |
|-----------------|-----------|
| 3分で全体像 | システム俯瞰力 |
| なぜ必要か / どの問題を解決するか | 設計判断力（背景理解） |
| 他の仕組みとどう関係するか | システム俯瞰力 / 症状追跡力 |
| 誤解されやすいポイント | AIレビュー力（AIも同じ誤りを犯す） |
| 設計のベストプラクティス | 設計判断力 |
| **AIエージェントとの協働** | **AIレビュー力（中核セクション）** |
| 理解度セルフチェック | 4スキル全て（自分の理解度を測り、答えられなければ本文に戻る） |

## 「コードを書く」と「AIに書かせる」の境界

各トピックのフロントマター `ai_collaboration: heavy | partial | minimal` がこの分類を示す。

### AIに任せやすい領域（heavy）
- ボイラープレート（CRUD・型定義・テスト雛形）
- 既知パターンの実装（バリデーション・認証フロー・ページネーション）
- 言語間の翻訳（Python→TypeScript 等）
- ドキュメント・コメント生成

### 人間判断が要る領域（minimal）
- アーキテクチャ選定（モノリス vs マイクロサービス、SQL vs NoSQL）
- セキュリティ境界の設計（認証フロー・トークン保管・CORS設定の採否）
- パフォーマンスのボトルネック特定（プロファイリング結果の解釈）
- データモデリング・スキーマ設計
- トレードオフの判断（一貫性 vs 可用性、可読性 vs 性能）

### 中間領域（partial）
- リファクタリング（AIが提案、人間が採否を判断）
- バグ修正（AIが原因仮説を出す、人間が検証）
- ライブラリ選定（AIが候補を出す、人間が文脈を踏まえて選ぶ）

## 本教材を使う5つの動作原則

### 1. 一度で覚えようとしない、何度も読み返す
本教材は **じっくり何度も読み込むことで効果がある読み物** として設計されている。初読では「3分で全体像」だけ拾い、本文は流し読みでも構わない。数週間後・数ヶ月後に同じトピックを読み直すと、経験を積んだぶん **初読時には素通りした記述の意味が立ち上がってくる**。これを繰り返すうちに、頭の中に立体的なインデックスが構築される。

### 2. 通読より「索引化」を優先する
全部を覚えようとしない。**「ここに何かあった」**と頭にインデックスがある状態を作る。詰まったときに Obsidian で該当ファイルを開ける状態がゴール。

### 3. 各トピックの「3分で全体像」を最重視する
本文より先に「3分で全体像」を読む。そこに書かれた **これだけは覚える3つ** が、AI出力をレビューする際の検閲点になる。

### 4. AI協働章を「教科書」ではなく「武器」と捉える
「AIエージェントとの協働」章にある **レビュー観点・効くプロンプトの型・アンチパターン** は、明日からのAI協働で実際に使う武器として読む。覚えるのではなく、参照できる状態にする。「N+1検出やセキュリティチェックは AI レビュー（AIコードレビュー観点）に任せ、人間は最終判断のみ」という協働モデルを身につける。

### 5. 詰まりは「症状→原因」のトレースで解決する
「動かない」「遅い」「セキュリティが心配」といった症状から、関連レイヤーへ降りる。`/diagnose` skill や [[_starter/02_実務症状からの逆引き]] を活用する。

## 学習の終わりはどこか

「全トピックを完了した」状態は、実は重要ではない。重要なのは:

- AIに何かを書かせるとき、関連トピックの **効くプロンプトの型** が思い浮かぶ
- AI生成コードを見て、関連トピックの **レビュー観点** が頭に浮かぶ
- 障害症状を見て、関連レイヤーへ自然に降りられる
- 設計判断を求められたとき、関連トピックの **誤解されやすいポイント・ベストプラクティス** を引ける

この状態を、最小学習パスの14トピック → 各レイヤー実践演習で構築する。

## なぜAIに「丸投げ」では危険なのか

AIコーディングエージェントは強力だが、以下の限界がある:

| 限界 | 例 | 教材での対策 |
|------|---|------------|
| **プロジェクトの暗黙の規約を知らない** | 既存ユーティリティを使わず再発明する | [[_anti-patterns/_index]] |
| **過剰な防御的コードを書きがち** | 起こりえないケースに try/catch | 各トピックのアンチパターン表 |
| **「動く」と「正しい」を区別しない** | テストが通れば良しとする | 理解度セルフチェック |
| **ハルシネーションする** | 存在しないAPIを使う | [[_starter/04_AI協働の基本動作]] |
| **セキュリティ判断ができない** | CORS全許可、認証スキップ等を提案する | Layer 6 トピック群 |

これらに対する**人間側の検閲機構**を、教材を通して身につける。
